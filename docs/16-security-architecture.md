# 平台安全架构与安全治理规范

> 状态：建议方案 / v0.1，待安全评审、业务评审与法律合规确认  
> 更新时间：2026-11-20  
> 适用范围：用户端、服务商端、企业端、运营管理端、开放API、微服务、数据采集系统及基础设施  
> 上游文档：02 商业模式与法律主体关系、04 支付与结算合规、05 产品架构、07 数据架构、08 技术架构、13 微服务系统架构设计、14 微服务边界与API接口契约、15 事件驱动架构与消息协作规范

## 1. 目标与安全边界

本规范建立平台的身份、授权、数据保护、服务间信任、支付安全、文件安全、市场数据采集安全、审计监控和应急响应基线。

安全设计目标：
1. 确保用户只能访问本人或其被授权组织的数据。
2. 确保服务商、施工企业、业主、平台运营人员的业务权限相互隔离。
3. 确保微服务只访问自身负责的数据和被明确授权的下游能力。
4. 确保支付状态以可信支付机构结果为准，防止伪造回调、重放和重复扣款。
5. 确保合同、报价、施工现场资料、个人信息和经营数据得到分级保护。
6. 确保市场情报采集遵守来源许可、访问限制和个人信息保护要求。
7. 确保高危操作可追踪、可审批、可追责和可恢复。

安全不能只依赖网关或登录页面。必须覆盖客户端、API、服务、数据库、消息、文件、运维和第三方集成的完整链路。

## 2. 威胁模型与保护对象

### 2.1 主要威胁

| 威胁 | 典型场景 | 主要控制 |
|---|---|---|
| 账号接管 | 撞库、弱密码、验证码滥用、会话窃取 | 多因素认证、限流、风险检测、会话撤销 |
| 越权访问 | 修改订单ID读取他人订单、跨企业访问 | 对象级授权、组织范围校验、审计 |
| 权限滥用 | 运营人员批量导出客户资料 | 最小权限、审批、导出水印和审计 |
| API攻击 | 注入、参数篡改、重放、批量爬取 | 输入校验、限流、签名、检测 |
| 服务身份伪造 | 非授权服务调用内部接口 | 服务身份认证、网络策略、短期凭据 |
| 数据泄露 | 日志、备份、对象存储或消息中暴露敏感数据 | 加密、脱敏、访问控制、保留策略 |
| 支付欺诈 | 伪造回调、重复通知、金额篡改 | 验签、金额核对、幂等、主动查询、对账 |
| 文件攻击 | 恶意文件、路径穿越、公开链接泄露 | 文件类型校验、隔离扫描、短期授权链接 |
| 采集合规风险 | 违反来源条款、抓取非必要个人信息 | 来源准入、采集策略、停止机制、数据治理 |
| 供应链风险 | 依赖包、镜像、CI凭据泄露 | 依赖扫描、镜像签名、密钥管理、发布审批 |
| 内部误操作 | 删除数据、错误退款、错误封禁 | 双人审批、软删除、备份、回滚和审计 |

### 2.2 重点保护资产

- 用户身份凭证、手机号、邮箱和账户安全信息。
- 个人住址、施工地址、联系方式、现场照片和定位信息。
- 企业主体资料、经营信息、人员信息和资质材料。
- 报价、合同、工程图纸、验收记录和争议证据。
- 支付订单、支付机构交易号、退款记录和对账数据。
- 服务商评价、风控标签、城市运营数据和平台经营数据。
- 市场采集来源、访问凭据、网页原文、解析结果和数据授权证明。
- 生产环境密钥、数据库凭据、对象存储凭据和运维权限。

## 3. 身份体系

### 3.1 用户身份与业务主体分离

用户账号代表自然人登录身份；组织代表企业或经营主体；平台业务角色代表用户在特定业务场景中的职责。三者不能混为一个字段。

建议核心实体：
- user：自然人账号及基础状态。
- credential：密码、短信验证器、第三方登录凭据等认证方式。
- organization：企业或其他组织主体。
- organization_member：用户与组织的成员关系。
- role / permission：角色和权限定义。
- user_session：登录会话和设备信息。
- identity_verification：必要的身份核验状态及核验记录引用。

同一用户可以加入多个组织，在不同组织中担任不同角色。用户退出组织、组织冻结或成员权限变更时，应能撤销或刷新对应会话授权。

### 3.2 认证方式

- 支持安全的密码哈希算法存储密码，禁止明文或可逆加密存储。
- 短信验证码应有有效期、尝试次数、发送频率和用途绑定。
- 对高风险操作、企业管理员、财务和平台运维账号，建议启用多因素认证。
- 第三方登录应校验回调状态、授权码、签发方、受众和有效期。
- 管理后台不应仅凭普通用户登录态获得管理权限。
- 登录失败、密码重置、设备变化和异常地理位置等行为应进入风险检测。
- 密码、手机号或认证器变更后，应提供撤销其他会话的能力。

认证成功只证明主体身份，不代表其有权访问某个订单、合同或企业资源。

### 3.3 会话与令牌

建议采用短时访问令牌与可撤销刷新会话的组合。具体令牌格式由技术选型确定。

要求：
- 访问令牌设置合理有效期，刷新令牌轮换并支持撤销。
- 浏览器会话优先使用安全Cookie策略；避免将长期凭据暴露给脚本。
- 移动端凭据存放于系统安全存储区域。
- 登出、账号冻结、密码重置和高风险事件可触发会话撤销。
- 令牌不得写入日志、URL、埋点或错误提示。
- 服务端校验签发方、受众、有效期、签名和必要的权限声明。
- 不将长期静态JWT当作服务间认证的唯一方案。

## 4. 授权模型：RBAC + ABAC

### 4.1 RBAC角色模型

建议平台角色按主体范围划分：

| 主体范围 | 角色示例 | 权限边界 |
|---|---|---|
| 普通用户 | 业主、需求发布者 | 本人需求、报价、合同、订单和售后 |
| 服务商组织 | 组织所有者、管理员、报价人员、项目负责人、施工人员 | 所属组织被授权的资源和操作 |
| 企业客户 | 企业管理员、项目负责人、采购、验收人员、财务查看人员 | 本企业项目和合同范围 |
| 平台运营 | 客服、审核、城市运营、内容治理 | 按岗位和工单范围访问 |
| 平台财务 | 对账、退款审核、结算运营 | 财务相关权限，关键操作分离 |
| 平台安全/审计 | 安全审计、合规审计 | 只读审计和受控调查 |
| 平台系统管理员 | 基础设施运维 | 系统配置，不默认拥有业务数据查看权 |

### 4.2 ABAC属性

除角色外，授权时还应检查：
- 资源所属用户ID。
- 资源所属组织ID。
- 组织成员关系及有效状态。
- 资源城市、项目、订单或合同范围。
- 资源当前状态。
- 数据敏感级别。
- 操作时间、设备风险和操作渠道。
- 是否存在有效授权、委托或工单。

示例：施工人员即使具有“施工人员”角色，也只能访问其所属组织分配给自己的项目；企业财务即使能查看付款状态，也不应自动获得现场照片和个人身份证件访问权。

### 4.3 对象级授权

每个涉及业务资源的API都必须在服务端校验对象级权限。禁止仅依赖前端隐藏按钮或网关角色判断。

检查流程：
1. 认证当前用户或服务身份。
2. 获取目标资源及其权威归属信息。
3. 检查用户与资源所有者/组织的关系。
4. 检查角色权限和ABAC条件。
5. 检查资源状态是否允许当前动作。
6. 记录敏感操作审计。

禁止使用客户端提交的organizationId、ownerId或role字段直接作为授权依据。

### 4.4 权限治理

- 默认拒绝，显式授权。
- 新角色上线必须有权限矩阵和测试。
- 权限变更记录操作者、审批人、变更前后值和生效时间。
- 组织管理员只能管理本组织成员，不得提升平台角色。
- 临时权限必须设置到期时间。
- 离职、退出组织和账号冻结应触发权限回收。
- 高危权限采用职责分离，申请人与审批人不得为同一人。

## 5. API Gateway 与外部接口安全

API Gateway负责统一入口治理，但业务服务仍须执行授权和数据校验。

网关职责：
- TLS终止或透传、域名与路由管理。
- 访问令牌初步校验。
- 请求体大小、连接数、频率和并发限制。
- 基础WAF规则、恶意请求拦截和IP风险策略。
- 请求ID、Trace上下文注入。
- API版本管理、灰度路由和基础访问日志。
- 对公开API、用户API、管理API和内部API实施不同策略。

业务服务职责：
- 对象级授权和组织范围校验。
- 业务状态校验、金额校验和幂等。
- 数据字段白名单、输入格式和业务规则验证。
- 敏感数据字段级访问控制。
- 业务审计事件。

安全要求：
- 仅通过受控入口暴露公网服务；数据库、消息代理和内部管理端口不得直接公网开放。
- 对登录、验证码、搜索、报价、文件上传和支付相关接口分别配置限流策略。
- 防止批量枚举资源ID和接口自动化滥用。
- CORS仅允许明确的可信来源，不使用任意来源加凭据的宽松配置。
- 管理API采用独立路由、独立权限策略和更严格的认证。
- 对Webhook提供签名、时间戳、随机数/事件ID和重放防护。

## 6. 微服务间安全

### 6.1 服务身份

每个微服务应具有独立服务身份，不共享一个全平台静态密钥。生产环境优先采用短期凭据、工作负载身份或双向TLS等方式，具体根据部署平台确定。

### 6.2 服务授权

- 服务身份认证与用户身份认证分开。
- 服务A只能调用授权清单中的服务B接口。
- 内部服务调用应声明调用方身份和必要的用户/组织上下文。
- 下游服务不能因为请求来自内网就跳过授权。
- 需要代表用户执行的操作应保留可信的委托上下文，不能伪造用户身份。
- 管理、财务、支付和身份服务使用更严格的访问策略。

### 6.3 数据库与消息访问

- 每个服务使用独立数据库账号，原则上只拥有自身Schema或数据库的必要权限。
- 禁止跨服务直接读写对方业务表；跨服务查询通过API、事件或专门只读分析模型。
- 数据库账号区分应用读写、迁移、只读分析和运维角色。
- 消息主题采用生产者/消费者ACL，按文档15执行。
- 密钥通过密钥管理服务或受控Secret系统注入，不写入Git仓库、镜像层和日志。
- 生产、预发、开发环境的凭据和网络边界必须隔离。

## 7. 数据分级与保护

### 7.1 建议分级

| 等级 | 数据示例 | 基本要求 |
|---|---|---|
| L1 公开 | 已审核公开的服务目录、公开企业信息 | 来源和授权记录，防篡改 |
| L2 内部 | 运营指标、非敏感配置、内部任务状态 | 身份认证、角色授权、访问审计 |
| L3 敏感 | 手机号、精确地址、合同、报价、现场照片、企业资质材料 | 加密、字段脱敏、严格授权、下载审计 |
| L4 高敏感 | 身份证件原文、支付凭据、认证密钥、特殊争议证据 | 强访问控制、最小留存、独立密钥/权限、严格审计 |

具体分级应由数据保护影响评估和法律合规评审确认。支付卡敏感认证数据等不得因业务便利而自行保存。

### 7.2 加密

- 外部通信使用TLS；内部敏感链路按风险采用TLS或双向TLS。
- 数据库、对象存储、备份和日志存储启用静态加密。
- 高敏感字段可采用字段级加密或令牌化。
- 加密密钥与数据分离存储，实施轮换、权限隔离和访问审计。
- 密钥不得硬编码在代码、前端包、CI日志或容器镜像。
- 加密算法和密钥长度遵循适用的国家标准、密码管理要求和安全评审。

### 7.3 脱敏与展示

- 手机号、证件号、地址、支付标识按岗位需要展示最少内容。
- 日志和链路追踪默认不记录完整手机号、证件、合同正文、支付凭据和精确地址。
- 测试环境使用合成或脱敏数据，生产数据导出到测试环境须经审批和脱敏。
- 数据导出应记录用途、操作者、范围、数量和时间；必要时加水印和到期失效。
- 分析模型优先使用去标识化数据。

### 7.4 生命周期

为不同数据类型定义收集目的、处理依据、保留期限、访问角色、删除/匿名化规则和法律保全例外。达到目的或保留期限后，按业务和法律要求删除、匿名化或限制访问。不得无期限保留所有原始网页、个人资料和附件。

## 8. 支付与资金安全

支付系统必须遵循文档04的主体关系和资金路径设计。技术安全控制不能替代持牌支付机构、银行产品适用性或法律合规判断。

核心要求：
1. 支付金额、币种、付款方、收款方和业务订单关联均由服务端根据权威业务数据计算。
2. 客户端不能决定最终支付金额、商户号、收款主体或退款账户。
3. 支付回调必须验证签名/证书、商户身份、应用身份、交易号、金额、币种和业务关联。
4. 回调事件ID或支付机构交易号必须幂等处理；重复通知不得重复记账或重复推进订单。
5. 回调乱序时，根据支付机构交易查询和状态机规则处理，不简单以最后到达事件覆盖状态。
6. 支付请求使用稳定幂等键，网络超时后先查询原交易，不盲目创建新交易。
7. 退款必须关联原支付交易、核验可退金额和已退款金额，并执行权限审批。
8. 支付状态、订单状态、合同状态和平台内部账务记录分开建模。
9. 对账差异进入异常队列，不能通过直接修改数据库余额消除差异。
10. 商户密钥、证书和回调配置纳入密钥管理与轮换。

平台不得仅凭内部账本或前端显示宣称已完成真实资金清算。资金归集、保管、划转、分账和结算安排必须由专业机构和法律顾问结合实际产品与合同关系确认。

## 9. 文件与对象存储安全

文件类型包括身份/资质材料、合同、工程图纸、施工现场照片、验收证据和售后附件。

上传要求：
- 使用服务端生成的对象键，不信任客户端文件名和路径。
- 校验文件大小、扩展名、MIME和文件真实格式。
- 限制文件类型和数量；压缩包、脚本、可执行文件默认拒绝或进入特殊审核。
- 对上传文件进行恶意软件扫描；扫描完成前置于隔离区。
- 图片可移除不必要的EXIF定位等元数据。
- 解析PDF、Office和图片时在隔离环境运行，限制CPU、内存和处理时间。
- 防止路径穿越、内容伪装、压缩炸弹和超大文件攻击。

下载要求：
- 私有桶默认禁止匿名访问。
- 使用短时效签名URL或经过鉴权的下载代理。
- 下载前执行资源级权限检查；签名URL有效期尽量短。
- 高敏感文件下载、预览和导出记录审计。
- 对合同和证据材料保留版本、摘要、上传人、时间和必要的完整性信息。
- 删除采用受控软删除/保留策略，涉及争议或法律保全时遵循保全规则。

## 10. 市场情报采集安全与来源治理

市场情报系统应将“可公开访问”与“允许自动化采集、存储、加工和商业使用”区分处理。

来源准入记录至少包括：
- source_id、来源名称、运营主体和官方域名。
- 来源类型、访问方式、授权/许可依据及适用条款。
- 允许采集的数据类别、目的、范围和频率。
- robots规则、API条款、限频要求和禁止行为（如适用）。
- 是否包含个人信息、敏感个人信息或用户生成内容。
- 数据存储、加工、展示、引用和删除限制。
- 责任人、审核人、审批时间、复核周期和停止条件。

采集控制：
- 优先使用官方API、开放数据和明确许可的数据源。
- 不绕过登录、验证码、付费墙、访问控制或技术保护措施。
- 不以代理池、伪装身份或高频请求规避来源限制。
- 尊重来源条款、robots规则及适用法律；robots规则本身不等于完整法律授权。
- 设置域名级并发、速率、重试和熔断策略。
- 对来源政策变化、投诉、授权到期或访问异常建立暂停机制。
- 采集原文、摘要和实体数据保留来源、采集时间、处理版本和授权依据。
- 对无必要的自然人联系方式、个人主页和个人行为信息不采集或及时删除。
- 企业主体候选进入交易平台前，必须由独立的服务商准入流程核验。

市场数据使用必须由产品、数据治理和法律人员共同确认用途边界；不得把公开网页上的个人信息当然视为可任意聚合、画像或营销使用。

## 11. 管理后台与高危操作

管理后台是高价值攻击面，应独立保护。

建议高危操作：
- 修改支付/退款状态或发起退款。
- 修改商户、支付机构、结算配置。
- 导出用户、企业或订单批量数据。
- 查看或下载高敏感证件、合同和争议证据。
- 修改组织管理员、平台角色和权限策略。
- 批量封禁账号、服务商或企业。
- 修改来源采集策略、批量删除或重算市场数据。
- 生产数据库写操作、消息重放和密钥轮换。

控制要求：
1. 高危操作重新认证或MFA。
2. 按风险执行双人审批，申请人与审批人分离。
3. 明确展示操作对象、影响范围和不可逆风险。
4. 记录操作前后值、原因、工单号、操作者、审批人和结果。
5. 支持操作限额、批量阈值和异常告警。
6. 对退款、资金配置和敏感数据导出采用更严格职责分离。
7. 紧急权限为限时授权，事后必须复核。

平台运营人员不得因“客服”角色默认获得查看所有用户证件、合同全文和支付敏感信息的权限。

## 12. 安全开发与供应链

开发流程应纳入安全检查：
- 代码评审检查鉴权、对象级授权、输入校验、日志脱敏和错误处理。
- SAST、依赖漏洞扫描、Secret扫描和容器镜像扫描。
- 构建产物可追溯，生产发布经过受控CI/CD身份授权。
- 依赖包锁定版本并定期升级；评估高危依赖和废弃组件。
- 生产环境禁止开发人员共享管理员账号。
- 数据库迁移使用独立凭据和审批流程。
- 对外部Webhook、SDK和第三方服务建立供应商安全评估。
- 定期进行API安全测试、渗透测试和权限矩阵回归测试。

重点测试：
- 越权读取其他用户订单和企业项目。
- 普通用户调用管理API。
- 服务商跨组织访问。
- 伪造和重放支付回调。
- 重复退款、金额篡改和支付状态乱序。
- 文件类型伪装、恶意文件和未授权下载。
- 注入、SSRF、路径穿越、批量枚举和限流绕过。
- 消息主题越权订阅和恶意事件注入。

## 13. 日志、审计与安全监控

日志分为应用运行日志、安全事件日志、业务审计日志和财务/交易证据记录。各自的用途、访问权限和保留期限应分别定义。

至少记录：
- 登录成功/失败、密码重置、MFA变更和会话撤销。
- 授权拒绝、跨组织访问尝试和权限变更。
- 敏感信息查看、下载和批量导出。
- 合同签署状态、支付回调验证、退款审批和对账异常。
- 服务身份认证失败、密钥轮换和管理配置变更。
- 市场来源准入、采集暂停、数据删除和授权变更。
- 生产环境登录、运维操作、数据库变更和消息重放。

审计记录应具备可信时间、主体、动作、对象、结果、来源IP/设备上下文（在必要范围内）、关联ID和操作原因。关键审计日志应防篡改、限制删除权限，并与普通应用日志分离。

监控告警包括账号异常、认证失败激增、越权访问、异常导出、支付验签失败、退款异常、来源限频违规、密钥异常使用和关键服务安全配置变化。

## 14. 备份、恢复与业务连续性

- 数据库、对象存储和必要配置制定备份策略。
- 备份加密、权限隔离，禁止生产应用账号删除备份。
- 备份副本与生产故障域隔离。
- 定期执行恢复演练，验证数据完整性和业务可用性。
- 明确RPO、RTO目标，按交易、合同、文件和市场情报数据的重要性分别确定。
- 对勒索软件、凭据泄露和数据误删制定应急预案。
- 备份中个人信息仍受访问控制、保留期限和删除治理约束。

## 15. 安全事件响应

建立分级响应机制，至少覆盖：
1. 发现：告警、用户投诉、第三方通知或内部巡检。
2. 分级：评估影响范围、数据类别、资金风险和服务可用性。
3. 遏制：撤销凭据、冻结账号、关闭接口、暂停采集或隔离服务。
4. 调查：保全日志、请求链路、事件ID、数据库审计和支付机构记录。
5. 恢复：修复漏洞、轮换密钥、恢复数据和验证业务状态。
6. 通知与报告：按适用法律法规、合同和监管要求履行通知、报告义务。
7. 复盘：根因分析、影响评估、改进项和责任人跟踪。

涉及个人信息或重要数据安全事件时，应由法务/合规、安全负责人根据适用法规判断通知、报告和处置义务及时间要求，不在本技术文档中自行设定法律结论。

## 16. 中国大陆合规建设关注点

平台在中国大陆运营时，应由法律顾问结合实际业务、数据流、主体关系和服务范围评估适用要求。重点关注但不限于：
- 《中华人民共和国网络安全法》及现行有效修订和配套规则。
- 《中华人民共和国数据安全法》。
- 《中华人民共和国个人信息保护法》。
- 网络数据安全管理相关行政法规和配套规定。
- 网络安全等级保护制度及适用的国家标准。
- 电子商务、消费者权益保护、电子签名、支付结算和行业资质相关要求。
- 数据跨境、重要数据识别、个人信息出境和第三方处理关系（如涉及）。

不得仅凭平台类型或用户规模直接断言适用某一等保级别、备案类别或许可结论。应进行系统定级、主管部门/专业机构沟通和正式测评确认。

## 17. MVP安全实施基线

首期上线前至少完成：

| 范围 | 必须完成 |
|---|---|
| 身份认证 | 密码安全存储、验证码限流、会话撤销、管理账号MFA |
| 访问控制 | 用户/组织/资源对象级授权，默认拒绝 |
| API | TLS、参数校验、限流、统一错误处理、管理API隔离 |
| 服务间 | 服务身份、最小权限、环境隔离、密钥不入库 |
| 数据 | 分类分级、敏感字段脱敏、数据库与备份加密 |
| 支付 | 回调验签、金额核对、幂等、防重放、主动查询和对账 |
| 文件 | 私有存储、文件类型校验、恶意文件扫描、短时授权下载 |
| 审计 | 登录、授权拒绝、敏感访问、退款和高危操作审计 |
| 采集 | 来源登记、授权/条款审查、限频、暂停与删除机制 |
| 运维 | 备份恢复演练、漏洞扫描、应急联系人和处置流程 |

未达到以上基线，不应开放真实资金交易或批量处理敏感个人信息。

## 18. 待确认事项

- 统一身份认证协议、令牌方案和会话存储实现。
- 企业组织、成员关系、委托授权和临时权限模型。
- 管理后台MFA和高危操作双人审批范围。
- 服务间身份方案（mTLS、工作负载身份或其他机制）。
- 数据分级目录、字段级加密范围和密钥管理服务。
- 文件扫描服务、对象存储和签名URL有效期。
- 支付机构回调协议、证书轮换和对账差错流程。
- 市场数据源许可审核责任人和周期。
- 等保定级、备案、测评及其他适用合规事项。
- 各类数据保留期限、删除规则和法律保全流程。
- 安全事件分级、通知机制和应急演练频率。

**结论：** 平台安全架构以身份可信、对象级授权、服务最小权限、数据分级保护、支付事实核验、来源合规治理和可审计运维为核心。网关、加密和消息认证只是基础控制，不能替代业务服务自身的授权判断与合规责任。
