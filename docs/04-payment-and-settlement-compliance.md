# 支付与结算合规设计

> 文档状态：讨论稿 / v0.1  
> 更新时间：2026-11-20  
> 适用范围：中国大陆境内水电安装服务与工程交易平台  
> 上游文档：01-business-positioning.md、02-business-model-and-legal-relationships.md、03-transaction-models.md  
> 重要说明：本文是产品与技术方案讨论稿，不构成法律意见、支付机构准入承诺或监管合规结论。具体业务结构须由中国大陆执业律师、税务专业人士及拟合作银行/持牌支付机构结合真实合同、账户和资金路径书面核验。

## 1. 设计目标与底线

支付系统的目标不是让平台“拥有用户的钱”，而是准确表达交易合同、支付请求、外部支付结果、退款、结算和对账事实。

平台应坚持以下底线：

1. **不自行经营未经许可的支付业务。** 平台不因开发余额、转账、提现、分账或资金冻结功能，就获得支付或清算资质。
2. **不归集、沉淀或控制第三方交易资金。** 不将业主支付的施工款先进入平台普通自有账户，再由平台自行向施工方转账。
3. **资金路径由真实交易关系决定。** 付款人、合同相对方、实际收款人、支付商户、结算账户及开票主体必须有可解释且一致的业务依据。
4. **支付服务由合适的银行或持牌支付机构提供。** 具体产品能力、许可范围、商户模式、交易场景和结算安排必须逐项确认。
5. **支付机构接入不自动消除平台风险。** 如果平台实际控制资金归集、决定向多个主体划款，或以技术结构掩盖真实交易关系，不能仅凭“接入了支付公司”认定合规。
6. **业务账本不等于资金账户。** 平台数据库只记录业务应收应付、支付请求、外部流水和对账差异，不代表用户资金实际存放于平台。
7. **所有资金动作可追溯、可核对、可审计。** 任何支付、退款、服务费扣收、分账或结算都必须有合同依据、授权依据、外部交易凭证和操作日志。

## 2. 法律和监管依据：事实与待确认边界

### 2.1 已有明确规则

- 《非银行支付机构监督管理条例》自2024年5月1日起施行。条例规定，非银行支付机构须依法取得支付业务许可；其定义围绕根据用户提交的电子支付指令转移货币资金等支付业务；条例还规定备付金管理、清算机构处理及支付机构不得从事或变相从事清算业务等要求。[国家行政法规库](https://xzfg.moj.gov.cn/front/law/detail?LawID=1696)
- 《非银行支付机构监督管理条例实施细则》由中国人民银行于2024年7月9日公布施行，进一步细化支付机构监管要求。[司法部官网](https://www.moj.gov.cn/pub/sfbgw/flfggz/flfggzbmgz/202504/t20250424_518044.html)
- 《银行卡收单业务管理办法》对收单机构、特约商户、收单协议和交易资金结算作出规定。收单业务的核心之一是收单机构为特约商户提供交易资金结算服务；商户身份、结算账户和交易真实性等事项需按适用规则及收单协议处理。[中国政府网文件](https://www.gov.cn/zhengce/2013-07/05/5023771/files/29267552d4984ded9977582b6fec7b49.pdf)
- 中国人民银行银发〔2021〕259号通知对支付受理终端、特约商户信息、交易监测等提出要求。实际经营场所、商户身份、结算账户和交易行为不能随意错配。[北京市政府政策页面](https://www.beijing.gov.cn/zhengce/zhengcefagui/qtwj/202204/t20220407_2655822.html)
- 《电子商务法》关于电子商务平台经营者、平台内经营者、交易信息保存、消费者权益和平台责任的规定，也会影响平台交易流程与记录义务。正式上线前应结合平台具体角色核验适用条款。

### 2.2 不能仅凭产品描述得出的结论

以下事项不能在未取得机构书面方案和法律意见前直接认定为合规：

- “平台二级商户”或“子商户”是否可以覆盖平台全部施工人员、个体工商户和企业。
- 一个主商户号下的多主体分账是否适用于本平台的交易模式。
- 先收款后分账、延迟结算、担保交易、冻结、解冻或自动退款是否属于拟合作机构许可产品的范围。
- 平台能否从施工价款中直接扣除平台服务费，以及该扣费在合同、支付指令、商户协议和发票上如何体现。
- 自然人施工人员能否作为某一具体收单产品的商户及其结算账户类型。
- 工程预付款、进度款、质保金是否能由某一支付产品按平台设定的节点进行分配或延迟结算。

**结论：** 法律允许的支付业务边界、支付机构具体产品规则和平台真实交易安排必须同时满足。不能只看支付机构销售人员的口头介绍。

## 3. 先识别交易模式，再决定资金路径

平台至少存在三类不同法律与资金结构，不能混为一谈。

### 3.1 第三方撮合：业主与服务商直接交易

典型关系：
- 业主与实际服务商形成施工服务合同。
- 平台与业主形成平台服务协议。
- 平台与服务商形成平台入驻/信息服务/交易规则协议。
- 施工价款的收款主体原则上应是施工合同中真实的收款权利主体，并由合作银行或持牌支付机构按其认可的商户结构完成收款与结算。
- 平台服务费依据平台服务合同另行收取，或采用经银行/持牌支付机构及法律顾问确认的合规产品安排。

平台不能把第三方施工价款作为自己的营业收入或自有资金。平台也不能自行决定将已收取的第三方资金划给不同施工主体。

### 3.2 平台自营：平台是实际施工合同主体

典型关系：
- 业主与平台经营主体签订施工合同。
- 平台经营主体对合同范围内的施工交付承担相应责任。
- 平台根据真实采购、用工、分包或服务合同向供应商、施工企业等付款。
- 业主向平台经营主体支付合同价款，平台按自身经营收入、成本、税务和合同责任处理。

此模式下平台不是单纯撮合方。必须先确认其经营范围、项目资质要求、施工组织能力、质量安全责任、保险安排、用工关系和税务处理。不得通过合同文字将实际第三方施工关系简单包装为平台自营。

### 3.3 代理或受托收付：高风险、需专项论证

如果平台代表某一方收款、代为付款、管理款项或根据自身判断向多个主体分配资金，必须明确：
- 委托人是谁，代理权限是什么。
- 收款账户的法律性质和账户控制人是谁。
- 资金所有权、占有、保管、返还和划付义务如何约定。
- 支付指令由谁发出、谁有权变更或撤销。
- 平台是否事实上从事支付、结算或资金归集活动。
- 是否存在适用的银行/支付机构产品和明确许可边界。

**MVP 不建议采用平台代收代付模式。** 仅写“受托代收”或“用户授权”不能自动排除支付业务合规风险。

## 4. 住宅服务交易资金路径

### 4.1 推荐的撮合模式路径

~~~text
业主
  |
  | 住宅施工合同价款支付指令
  v
银行 / 持牌支付机构提供的合规收款产品
  |
  | 按已核验的商户结构及结算规则处理
  v
真实施工合同收款主体的结算账户

业主 -----------------> 平台经营主体
       平台服务费（依据独立平台服务协议）
~~~

该图表达业务原则，不代表任一支付机构都提供相同产品。实际收款产品可能要求施工服务商独立进件、独立商户号、特定场景证明、合同/订单信息、结算账户验证和交易风险管理。

### 4.2 不推荐的资金路径

~~~text
业主
  |
  v
平台普通公司账户 / 平台自有钱包
  |
  | 平台自行记账、扣费、决定何时及向谁转账
  v
施工人员 / 施工企业
~~~

该结构容易使平台形成对第三方交易资金的归集和控制。不得把它作为默认 MVP 方案，也不得通过“内部余额”“托管账户”或“项目资金池”等命名规避实质判断。

### 4.3 平台服务费收取

优先评估两种安排：

1. **独立收费：** 业主或服务商依据平台服务协议，向平台支付明确的平台服务费。施工合同价款仍按施工合同关系支付给服务商。
2. **机构产品支持的合规费用处理：** 若拟由支付机构在结算流程中处理平台服务费，应由机构明确确认其产品、商户结构、费用授权、资金流、退款处理、对账和税务凭证安排，并由律师审查合同。

不得在没有机构确认的情况下，把“自动扣点”当作普通数据库规则上线。

### 4.4 自然人施工服务商

若允许自然人直接承接订单，应先确认：
- 该自然人是否属于适用收单规则下可入网的经营主体/小微商户类别。
- 是否需要个体工商户或其他经营登记。
- 其结算账户是否符合机构要求。
- 服务内容是否涉及依法需要资质或许可的施工范围。
- 交易凭证、发票或税务处理如何完成。
- 其与平台是否存在劳动关系或其他用工法律关系。

不能仅凭身份证实名认证就认定其可以承接所有工程，也不能仅凭“个人接单”就确定其结算路径。

## 5. 商业工程项目资金路径

商业工程应以合同为中心，而不是以平台项目总金额为中心。

### 5.1 第三方承包主体直接签约

~~~text
项目业主 / 建设单位
  |
  | 工程合同（预付款、进度款、结算款等）
  v
施工企业 / 合法承包主体
  |
  | 其自身采购、分包、劳务等真实合同
  v
供应商 / 分包商 / 劳务服务主体

平台 <----> 项目双方
  平台服务合同、信息服务费或项目服务费
~~~

每份工程合同应独立识别签约主体、收款权利人、付款条件、发票责任和结算账户。平台不应把一个项目的全部工程款收进平台账户后再自行拆分。

### 5.2 多专业包、多承包商

一个 Project 可以包含多个 ProjectPackage，每个专业包可能对应不同承包主体和合同。资金安排应按各自合同分别确认，不能仅因这些合同属于同一个 Project 就自动合并收款或统一分配。

### 5.3 进度款与质保金

产品应记录合同约定的预付款条件、进度款申请及工程量/节点依据、变更签证对合同价款的影响、竣工结算依据和确认结果，以及质保金或其他尾款的合同依据、到期条件和支付结果。

平台可以记录“应申请”“已申请”“审核通过”“待支付”等业务状态，但不能自行保管质保金或以平台内部冻结余额替代合同与支付机构认可的资金安排。

### 5.4 法定招投标及工程监管边界

商业工程是否依法必须招标、承包主体是否需要资质、专业工程如何分包、合同是否需要备案或履行其他监管要求，应依据项目性质、资金来源、工程类别、规模和适用法律判断。平台的报名、竞价和中选模块不能被宣传为可以替代法定招投标或工程监管程序。

## 6. 银行/持牌支付机构合作准入清单

在产品开发前，至少向候选机构提交完整业务说明，并要求对方书面回答：

### 6.1 机构及许可
- 合作主体的完整法定名称和许可证/业务资格信息。
- 许可业务类型、地域、线上/线下场景及适用边界。
- 实际提供收单、支付、清算、结算服务的主体分别是谁。
- 是否涉及其他服务商或技术服务商，责任如何划分。

### 6.2 商户进件
- 平台本身是否需要进件。
- 施工人员、个体工商户、施工企业分别如何进件。
- 自然人能否入网，具体条件和结算账户要求是什么。
- 是否支持一个项目多个合同主体、多个收款商户。
- 商户经营范围、施工范围、资质和交易真实性材料要求。
- 商户变更、退出、冻结、风险处置流程。

### 6.3 收款、分账与结算
- 谁是交易商户和合同收款权利人。
- 资金实际经过哪些账户和清算链路。
- 是否有分账产品，分账参与方是否都需进件。
- 分账指令由谁发出，平台是否可自行决定收款人和金额。
- 是否支持延迟结算、部分结算、结算周期和风险延迟。
- 退款、部分退款、撤销、差错处理如何执行。
- 交易失败、商户退出、账户异常时资金如何处理。
- 质保金、争议款或冻结款是否属于产品支持范围，法律依据和控制权属于谁。

### 6.4 对账、数据和运营
- 交易、退款、手续费、结算的日对账文件格式。
- 是否提供订单号、支付单号、商户号、结算批次号等关联标识。
- 回调签名、重试、查询接口、幂等机制和通知时效。
- 差错处理时限和双方责任。
- 交易记录及商户资料保存要求。
- 数据处理、跨境访问、个人信息保护和安全审计安排。
- 费率、结算周期、保证金或风险准备金安排及其合同依据。

**机构口头承诺不作为上线依据。** 关键产品能力和资金路径须保留正式产品协议、技术文档、商户协议、结算规则及书面答复。

## 7. 平台内部业务账本与支付记录

平台可以建设业务账本，但必须明确它不是银行存款账户、支付账户或用户可提现钱包。

### 7.1 建议记录的业务对象

| 对象 | 作用 | 不能代表什么 |
|---|---|---|
| TradeAmountSnapshot | 保存报价/合同/变更金额快照 | 不能代表已收款 |
| PaymentRequest | 记录发起给机构的支付请求 | 不能代表支付成功 |
| ExternalPayment | 保存机构返回的支付流水及状态 | 不能代表已结算到商户 |
| RefundRequest | 记录退款申请及审批 | 不能代表退款已到账 |
| ExternalRefund | 保存机构退款流水和结果 | 不能代表所有资金差异已解决 |
| PlatformFeeReceivable | 记录平台服务费应收 | 不能代表已收款或可直接扣款 |
| SettlementStatement | 保存机构提供的结算结果 | 不能代表平台账户资金 |
| ReconciliationCase | 记录账单差异和处理过程 | 不能自动调整外部资金 |
| AuditEvent | 记录人工和系统操作 | 不能替代外部凭证 |

### 7.2 不建议的产品概念

MVP 不应向用户提供：
- 可充值、可提现、可转账的“平台钱包”。
- 可在不同商户之间转移的“平台余额”。
- 平台自行决定划转的“托管资金”。
- 没有真实银行/支付机构产品支持的“资金冻结/解冻”。
- 将商户应收款展示为平台保管的现金余额。

如果后续确有余额、预付、储值或资金管理需求，必须先单独做法律和支付许可论证，不作为普通功能迭代。

### 7.3 状态必须分层

不要只设置一个 payment_status。至少区分：
- 业务付款义务：未到付款节点、待支付、部分支付、已满足合同付款条件、争议中。
- 支付请求：未创建、已创建、已提交、处理中、失败、已关闭。
- 外部支付结果：成功、失败、撤销、退款中、部分退款、已退款。
- 机构结算结果：未结算、结算处理中、已结算、延迟结算、结算失败。
- 平台服务费：应收、已开票（如适用）、已收、退款/冲销、争议。

每一层都有独立事实来源，不能通过修改订单状态来伪造支付成功。

## 8. 支付技术流程与控制

### 8.1 发起支付

1. 校验订单/合同有效性和当前付款节点。
2. 根据真实签约主体确定收款商户和机构产品。
3. 创建平台内部唯一 payment_request_id。
4. 调用机构支付接口，保存机构返回的交易标识。
5. 前端展示“支付处理中”，不要仅凭客户端跳转或前端返回判定成功。
6. 接收机构异步通知并验签。
7. 必要时主动向机构查询最终状态。
8. 以机构可核验的成功结果更新外部支付记录。
9. 记录请求摘要、响应摘要、时间和审计事件，敏感数据按要求脱敏。

### 8.2 幂等和并发

- 同一业务付款节点设置唯一业务幂等键。
- 重复点击支付不得重复创建有效支付交易。
- 支付回调按机构交易号和事件号去重。
- 状态只能按允许的状态转换推进，不能由失败回调覆盖成功状态。
- 并发退款、部分退款和原交易金额必须进行原子校验。
- 超时不等于失败；应主动查询或等待机构最终通知。

### 8.3 退款

退款应满足：
- 关联原始支付交易。
- 核验原支付商户、退款权限和退款余额。
- 依据合同、取消规则、验收结果或争议处理结论。
- 通过原支付机构或其认可流程发起。
- 记录全额/部分退款、原因、审批人和外部退款流水。
- 退款失败时进入人工处理与对账队列。

不得由平台将其他用户或其他商户的资金用于垫付退款，除非属于平台自营合同下有明确法律和财务依据的自有资金支付。

## 9. 对账体系

### 9.1 三方核对

至少核对：
1. 平台业务记录：订单、合同、付款节点、退款和平台服务费。
2. 支付机构账单：支付、撤销、退款、手续费、分账（如适用）。
3. 商户/平台银行账户流水：真实结算到账和银行退汇等记录。

平台业务账本与外部账单不一致时，不能直接改账“对平”，必须形成差异案件。

### 9.2 对账维度

- 平台订单号。
- 合同号及付款节点号。
- 平台 payment_request_id。
- 支付机构交易号。
- 商户号及结算账户标识（敏感信息脱敏/令牌化）。
- 交易金额、退款金额、手续费。
- 交易日期、结算日期和结算批次。
- 外部状态、平台状态和差异原因。

### 9.3 差异处理类型

- 平台有支付请求，机构无交易。
- 机构支付成功，平台未收到回调。
- 平台记录成功，机构查询失败。
- 机构已退款，平台未更新。
- 机构结算成功，商户未确认到账。
- 金额、手续费或结算账户不一致。
- 重复通知、重复退款或重复结算文件。
- 商户状态变化导致结算延迟或失败。

所有差异需有责任人、处理时限、证据附件、处理结论和复核记录。严禁通过直接改数据库状态掩盖差异。

## 10. 发票、税务与收入确认

产品必须区分不同法律主体和不同收入性质：

- 施工服务收入：由实际施工合同项下依法承担开票义务的主体按适用税法处理。
- 平台服务收入：由实际提供平台服务并收取服务费的主体按适用税法处理。
- 材料销售收入：由真实销售主体按销售合同和适用税法处理。
- 平台自营工程收入：若平台是真实施工合同主体，应按其实际经营模式处理收入、成本、分包、采购和相关税务事项。

平台不能把第三方商户的施工合同全额简单确认为平台营业收入，也不能仅凭支付流水决定收入确认。收入确认、开票主体、代扣代缴、自然人劳务税务处理和跨主体费用结算需由税务专业人士按实际合同和业务流程确认。

系统应分别记录合同价款、平台服务费、材料价款、税费口径、发票申请/开具信息及退款红冲关联，但不应替代财税专业判断。

## 11. 二清风险识别与上线阻断清单

以下情形属于必须暂停并进行专项法律/支付合规审查的高风险信号，不在本文中对具体行为作抽象定罪判断：

- 业主向平台普通账户支付第三方施工款，平台再自行转给服务商。
- 平台统一归集多家商户资金，并自行决定分配对象、金额或时间。
- 平台为多个独立商户设置可相互转移的内部余额。
- 平台通过虚构交易、拆分订单或借用商户号改变真实收款主体。
- 商户没有独立、真实的交易和经营资料，支付商户与合同主体长期不一致。
- 平台控制支付账户、资金密码或结算账户，能够绕开机构规则划款。
- 以“托管”“担保”“保证金”“代收代付”等名称掩盖平台对资金的实际控制。
- 通过个人账户收取本应由企业商户收取的工程款，且无合法、适用的收单安排。
- 未经机构和法律顾问确认，平台自行实现分账、延迟结算、冻结或解冻。
- 支付成功、结算到账和平台业务完成被错误地合并为一个状态。

### 上线阻断条件

以下任一项未完成，不应开放真实交易收款：
1. 明确每类交易的真实合同主体、收款权利人和开票主体。
2. 明确资金从付款人到最终收款人的完整账户路径。
3. 取得银行/持牌支付机构对商户结构和场景适用性的正式确认。
4. 完成平台协议、商户协议、用户合同和退款规则审查。
5. 完成支付、退款、结算和对账的端到端联调与异常演练。
6. 明确商户准入、风险监测、交易真实性和退出处理机制。
7. 明确个人信息、交易记录和财务凭证的保存与访问控制。
8. 完成法律、支付机构、财税三方专项审查并留存结论。

## 12. MVP 推荐方案

### 12.1 首期资金模式

推荐优先采用**第三方撮合 + 施工服务商作为真实交易收款主体 + 银行/持牌支付机构提供经确认的支付产品 + 平台服务费独立收取**。

这只是优先评估方案，不代表所有支付机构都能支持，也不代表自然人服务商一定可以直接进件。

### 12.2 MVP 产品边界

首期实现：
- 订单、合同金额和付款节点记录。
- 服务商商户进件状态（调用机构能力或记录机构结果）。
- 外部支付请求及支付结果查询。
- 退款请求、退款结果和异常队列。
- 平台服务费应收与实收记录。
- 机构账单导入/获取和日对账。
- 交易审计、操作留痕和权限控制。

首期不实现：
- 平台自有可提现钱包。
- 平台普通账户代收第三方施工款。
- 平台自行控制的分账/冻结/解冻引擎。
- 脱离合同的任意余额调整。
- 把机构未确认的担保交易或资金托管包装成平台能力。

### 12.3 开发前的机构验证

先选 2—3 家银行或持牌支付机构，使用同一份业务流程说明进行方案评估。逐项核验：
- 住宅个人/个体工商户/企业服务商进件条件。
- 商业工程企业商户进件及多合同主体支持情况。
- 服务费独立收取或机构产品内处理能力。
- 退款、部分退款、延迟结算和风险处置。
- 对账文件、接口、费率和结算周期。
- 真实资金路径及合同文件要求。

在拿到机构正式方案前，支付接口只定义抽象适配边界，不假设某个支付渠道一定支持分账或担保。

## 13. 待确认事项

| 决策 | 推荐初值 | 需要确认 |
|---|---|---|
| MVP 交易角色 | 平台撮合方 | 是否存在任何自营施工业务 |
| 住宅收款主体 | 真实施工合同服务商 | 自然人、个体户、企业各自的准入方式 |
| 平台服务费 | 独立收费优先 | 由谁支付、何时收取、退款如何处理 |
| 工程款结算 | 合同主体对应商户结算 | 是否存在经机构确认的项目级多方结算方案 |
| 分账 | 不作为 MVP 前提 | 机构许可产品、参与方进件和指令控制边界 |
| 延迟结算 | 不自行控制 | 是否由机构产品按规则提供 |
| 质保金 | 合同约定并由合法主体/产品处理 | 是否需要第三方资金管理安排 |
| 自然人服务商 | 先审查再开放 | 商户身份、税务、资质和用工关系 |
| 材料交易 | 首期不由平台归集材料款 | 未来材料商是否独立签约、独立收款 |
