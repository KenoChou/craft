# 技术架构与系统演进

> 文档状态：讨论稿 / v0.1  
> 更新时间：2026-11-20  
> 适用范围：中国大陆水电安装服务与工程交易平台  
> 上游文档：01 商业定位、02 商业模式与法律主体关系、03 交易模型、04 支付与结算合规、05 产品架构、06 业务规则与流程、07 数据架构  
> 本文目标：将业务领域模型转化为可落地的系统结构，明确首期技术选型原则、模块边界、部署方式、关键链路、可靠性和容量演进策略。

## 1. 技术架构目标与约束

技术架构首先服务于真实业务闭环，而不是追求技术复杂度。首期系统必须能够可靠支持：
- 业主发布住宅水电安装、维修和局部改造需求。
- 服务商准入、报价、合同确认和施工履约。
- 商业工程项目线索及承包商撮合（按MVP实际范围启用）。
- 预约、施工记录、变更、验收、售后和投诉。
- 与银行或持牌支付机构进行支付、退款、结算状态同步及对账。
- 平台运营人员进行审核、派单、风控和争议处理。
- 关键交易操作具备身份授权、审计、幂等和证据追溯能力。

### 1.1 架构原则

1. **业务边界优先：** 以07数据架构定义的领域为模块边界，不以页面或数据库表作为唯一模块划分依据。
2. **模块化单体优先：** MVP先采用模块化单体，降低部署、调试和事务协调成本。
3. **交易事实可靠：** 合同、订单、支付和验收的关键状态必须由服务端规则控制。
4. **外部资金机构负责资金处理：** 平台负责业务支付编排和状态核对，不自建资金池或可划转用户余额。
5. **异步任务可恢复：** 消息、回调、通知和对账任务必须可重试、去重和补偿。
6. **安全默认开启：** 最小权限、敏感数据保护、审计、备份和漏洞管理不作为后期附加项。
7. **按数据和流量演进：** 只有在出现明确瓶颈、团队具备运维能力且收益可量化时才拆分服务。
8. **不为100万DAU提前过度设计：** 100万DAU是长期容量目标，不是首期同时在线人数，也不能直接推导出固定服务器数量。

## 2. 总体系统结构

建议采用分层、模块化的应用架构：

- **客户端层：** 业主端、服务商端、企业端、运营管理后台。
- **接入层：** HTTPS入口、反向代理/WAF、API路由、限流和基础防护。
- **应用层：** 模块化业务应用，按领域组织模块和接口。
- **基础设施层：** MySQL、Redis、对象存储、消息队列、搜索（需要时）、任务调度。
- **外部服务层：** 短信/推送、地图地理服务、实名认证服务、电子签约服务、银行/持牌支付机构。
- **运维治理层：** 日志、指标、链路追踪、告警、审计、备份和灾难恢复。

客户端不直接访问数据库或支付机构密钥。所有交易写操作必须经服务端鉴权、授权和业务规则校验。

## 3. 客户端与终端边界

### 3.1 业主端

主要能力：
- 手机号/适用方式登录和账户管理。
- 发布需求、上传现场图片和必要资料。
- 查看服务商资料、报价和服务范围。
- 比较报价、确认合同及变更。
- 预约进场、查看施工记录和验收。
- 按合同和支付机构流程完成付款、退款申请。
- 发起售后、投诉和评价。

业主端只展示其有权访问的交易数据。精确地址、联系方式和现场影像按交易阶段和授权范围披露。

### 3.2 服务商端

个人服务人员、个体经营者和企业服务商可以共用部分客户端能力，但界面权限由经营主体和组织成员关系决定。

主要能力：
- 个人/组织资料及准入状态。
- 服务类目、服务区域、接单状态和排期。
- 需求查看、报名、报价及报价版本。
- 合同查看、签署和变更确认。
- 施工任务、人员安排、现场记录和材料记录。
- 验收、整改、售后和结算状态查看。
- 企业成员邀请、角色授权和项目协作。

不得将企业负责人账号默认共享给所有施工人员；成员使用独立账户，按角色和项目范围授权。

### 3.3 企业与工程端

工程发包方、承包商和专业施工企业可使用企业工作台处理企业主体和成员管理、项目及专业包发布、承包商报名、报价和资格资料、项目合同、进度申报、检查和工程变更、项目人员、材料和文件协作、阶段付款申请、结算及质保事项。

商业工程功能按业务成熟度分阶段开放，首期不应为了完整企业工作台而拖延住宅交易闭环。

### 3.4 运营管理后台

后台采用独立权限体系和强制操作审计，主要包括用户、组织、服务商及资格审核；需求审核、异常需求处理和撮合辅助；订单、合同、施工、验收和售后监督；支付状态查询、退款审批（仅在授权范围内）和对账差异处理；投诉、争议、风险事件和平台规则管理；内容、类目、区域、服务费和运营配置；运营指标和审计查询。

运营人员不得直接修改支付成功、退款成功、合同生效等核心事实状态。需要纠正时必须通过有权限的业务操作或差错处理流程完成。

## 4. MVP应用架构：模块化单体

建议首期采用一个主要业务后端应用，内部按领域模块组织。模块之间通过明确的应用服务接口交互，不允许任意跨模块读写内部数据。

| 模块 | 主要职责 | 关键对象 |
|---|---|---|
| identity | 账户、认证、会话 | User、Credential |
| organization | 组织、成员、授权 | Organization、OrganizationMember |
| provider | 服务商资料、能力和准入 | ProviderProfile、Qualification |
| catalog | 服务目录、需求字段配置 | ServiceCategory、ServiceItem |
| geography | 区域、地址、服务范围 | Region、Address、ServiceArea |
| demand | 需求发布、审核、关闭 | Demand、DemandEvent |
| matching | 撮合、邀请、派单 | Match、Invitation |
| quotation | 报价、报价版本 | Quotation、QuotationVersion |
| contract | 合同主体、版本、变更 | Contract、ContractParty、ContractChange |
| service-order | 住宅订单、预约、施工、验收 | ServiceOrder、WorkLog、Acceptance |
| project | 商业项目、专业包、进度 | Project、ProjectPackage、ProgressClaim |
| payment | 支付编排、退款、结算和对账 | PaymentIntent、PaymentTransaction、Refund |
| after-sales | 售后、投诉、争议 | AfterSalesCase、Complaint、Dispute |
| file | 文件元数据、访问控制 | FileAsset、Evidence |
| notification | 站内信、短信和推送 | Message、Notification |
| review | 评价和信用事件 | Review、CreditEvent |
| operation | 平台运营、审核、风控 | ReviewTask、RiskCase |
| audit | 操作审计、业务事件 | AuditEvent、BusinessEvent |

### 4.1 模块依赖规则

- 客户端只能调用对外API，不访问模块内部实现。
- 模块之间优先调用公开应用服务接口。
- 跨模块查询通过明确的查询服务或只读投影实现。
- 不允许一个模块直接更新另一个模块的数据表。
- 支付模块不能绕过合同和付款计划自行决定应付金额。
- 订单模块不能根据前端传入的状态直接完成验收或关闭交易。
- 审计模块接收关键业务操作的审计事实，业务模块负责在正确时点产生事件。

### 4.2 何时拆分服务

只有满足以下一项或多项并经评估后，才考虑独立部署某个模块：独立模块出现明显且持续的资源瓶颈；不同模块有显著不同的可用性或扩缩容要求；模块需要独立发布且发布耦合影响交付；团队和运维能力能够承担分布式调用、故障隔离、链路追踪和数据一致性成本；存在明确的安全隔离或合规边界要求。

可能较早独立的候选包括文件处理、通知投递、搜索索引和支付机构适配服务，但不是MVP的强制拆分项。

## 5. 服务端接口与API设计

### 5.1 API边界

建议采用版本化HTTP API，例如 /api/v1/...。接口按业务资源组织，写操作表达业务命令，而不是允许客户端任意修改数据库字段。

示例：
- POST /api/v1/demands：创建需求。
- POST /api/v1/demands/{id}/submit：提交需求审核。
- POST /api/v1/quotations：提交报价。
- POST /api/v1/quotations/{id}/accept：接受报价。
- POST /api/v1/contracts/{id}/confirm：确认合同版本。
- POST /api/v1/service-orders/{id}/schedule：确认预约。
- POST /api/v1/service-orders/{id}/acceptance：提交验收申请或结果。
- POST /api/v1/payment-intents：创建支付请求。
- POST /api/v1/refunds：申请退款。

具体路径和命令语义在API规范阶段进一步统一。接口响应应包含稳定业务编号、状态、必要版本号和可追踪请求标识。

### 5.2 认证与授权

- 登录认证与业务授权分离。
- 访问令牌应有合理有效期、撤销机制和安全存储方式。
- 高风险操作可要求二次验证或重新确认身份。
- 每次请求均校验用户、组织成员状态、角色、资源归属和操作范围。
- 企业成员权限应支持组织级和项目级边界。
- 关键合同和资金操作需校验明确授权，不能只依赖“管理员”角色名称。
- 运营后台使用独立角色、强认证和操作审计。

### 5.3 幂等与并发

对创建支付请求、接受报价、确认合同、提交验收、申请退款等写操作支持幂等键或业务唯一约束。关键对象使用版本号或乐观锁，避免并发请求重复接受报价、重复创建支付义务或覆盖合同版本。

### 5.4 API安全

参数校验和服务端权限校验；登录、短信验证码和高风险接口限流；防止越权访问、重放、批量枚举和恶意文件上传；文件下载采用受控授权链接或服务端鉴权；对外接口设置请求体大小、超时和速率限制；敏感字段在日志和错误响应中脱敏；对关键接口建立安全测试和滥用监测。

## 6. 核心交易状态机

状态机属于服务端领域规则，不由客户端自由指定状态。

### 6.1 需求状态

建议初始状态集合：DRAFT（草稿）、SUBMITTED（已提交）、UNDER_REVIEW（审核中）、NEEDS_INFO（待补充）、PUBLISHED（已发布）、MATCHING（撮合中）、CONTRACTED（已形成合同）、PAUSED（已暂停）、CLOSED（已关闭）、REJECTED（审核拒绝）。

实际状态应在产品规则中精简，避免状态过多。每次转换记录操作者、原因、时间和前后状态。

### 6.2 报价状态

可包括 DRAFT、SUBMITTED、WITHDRAWN、EXPIRED、ACCEPTED、REJECTED。报价被接受时必须校验报价版本仍有效、需求仍可交易、服务商准入仍有效，并保证同一交易选择动作幂等。

### 6.3 合同状态

可包括 DRAFT、PENDING_CONFIRMATION、EFFECTIVE、PERFORMING、COMPLETED、TERMINATED、DISPUTED。合同生效条件应按签约方式和合同约定确定，不能仅以“用户点过按钮”作为唯一依据。

### 6.4 住宅订单状态

可包括 PENDING_SCHEDULE、SCHEDULED、IN_PROGRESS、PENDING_ACCEPTANCE、RECTIFICATION、COMPLETED、CANCELLED、AFTER_SALES。订单状态与支付状态分开管理；付款成功不自动代表施工完成，订单完成也不自动代表资金已结算。

### 6.5 支付状态

支付请求可区分 CREATED、PENDING、SUCCEEDED、FAILED、CLOSED；退款请求可区分 REQUESTED、PROCESSING、SUCCEEDED、FAILED、REJECTED；结算记录可区分 PENDING、PROCESSING、SETTLED、FAILED、RECONCILIATION_REQUIRED。

最终状态以合作机构可验证的交易/结算结果为准。回调未到达时应主动查询；回调重复到达时必须幂等处理。

## 7. 支付机构集成架构

### 7.1 适配层

建立统一的PaymentProviderAdapter接口，封装不同合作银行或持牌支付机构的商户进件及状态查询、支付订单创建、支付结果查询、退款申请及结果查询、合作机构提供的分账/结算能力（仅在具体产品和业务关系允许时）、对账文件获取及解析、回调验签和证书/密钥轮换。

统一接口不意味着不同机构的资金产品在法律和业务上完全等价。每个机构、产品、商户类型和业务场景都要单独配置和审核。

### 7.2 支付链路

1. 业务模块根据合同和付款计划生成应付节点。
2. 服务端校验付款义务方、收款权利主体、合同状态、金额和支付产品适用条件。
3. Payment模块创建本地PaymentIntent并生成唯一幂等业务号。
4. 通过适配层请求合作机构创建支付交易。
5. 客户端按机构提供的方式完成支付。
6. 服务端接收回调，验证签名、商户、金额、订单号、时间和状态。
7. 记录外部PaymentTransaction，并以幂等方式更新业务支付状态。
8. 定时主动查询长时间未决交易。
9. 接收或拉取结算信息，进行业务账与机构账对账。
10. 发生差异时进入人工/自动差错处理流程，保留完整处理记录。

### 7.3 资金边界

- 平台业务数据库只保存支付请求和外部机构交易事实，不保存可自由支配的用户资金余额。
- 不通过平台普通银行账户归集本应由交易主体或支付机构处理的交易资金。
- 不以“内部账本”“虚拟钱包”“分账记录”替代支付许可或合规资金结算安排。
- 不默认所有支付机构都支持平台自定义分账；必须核对产品合同、适用场景、商户关系和监管要求。
- 平台服务费与服务商工程款应有清晰合同依据、收费对象、开票主体和资金路径。
- 支付方案上线前由支付合作机构、法律顾问和财税顾问共同核验。

## 8. 数据与基础设施选型原则

| 组件 | MVP用途 | 选型原则 |
|---|---|---|
| 关系型数据库 | 交易主数据、合同、订单、支付流水 | 优先MySQL或兼容的成熟关系型数据库；做好索引、备份和主从监控 |
| Redis | 缓存、验证码限流、短期幂等辅助、分布式协调（谨慎） | 不作为合同、支付等核心事实的唯一存储 |
| 对象存储 | 图片、合同附件、施工影像、工程资料 | 私有桶、临时授权访问、生命周期和备份策略 |
| 消息队列 | 通知、异步任务、领域事件投递 | 需要时引入；必须支持重试、死信和消费幂等 |
| 搜索引擎 | 服务商、项目和内容检索 | 首期可先用数据库检索，数据量和检索需求明确后再引入 |
| CDN | 静态资源和适合缓存的公开内容 | 私有交易文件不得使用无授权的公开缓存 |
| 定时任务 | 超时提醒、支付查询、对账和数据清理 | 任务可重入、可观测、可补偿，避免单机内存定时器承担唯一调度职责 |

数据库主库承载交易事实。缓存丢失不得导致合同、订单或支付事实丢失。

## 9. 文件、地图、电子签约与通知集成

### 9.1 文件上传

上传链路应包含文件类型和大小校验、恶意文件检测、对象存储隔离、访问权限、元数据登记和审计。合同、身份证明、施工照片和工程图纸使用不同访问策略。公开展示图与交易证据文件应分开管理。

### 9.2 地图与地址

地图服务用于地址选择、地理编码、区域匹配和路线辅助。精确地址只向交易必要参与者披露；对外列表使用模糊位置或区域级信息。地图供应商的坐标、地理编码和数据使用条款需要单独评估。

### 9.3 电子签约

如接入第三方电子签约服务，需核验签署主体、签署意愿、身份认证、签署过程证据、合同版本完整性、签署结果回调和文件归档。平台自行保存一个“已签署”布尔值不能替代可靠签署证据。

### 9.4 通知

站内通知作为基础能力；短信、推送和其他通知渠道按成本和必要性接入。通知失败应可重试，重要交易动作不能仅依赖通知送达触发状态变化。

## 10. 安全与隐私保护

### 10.1 身份与访问控制

采用最小权限原则，按用户、组织、项目和交易资源进行授权。服务端必须校验资源归属，不能只依赖客户端隐藏按钮。运营人员、财务人员和审核人员权限应分离。

### 10.2 敏感数据

- 身份证件、联系方式、精确地址和银行/支付相关标识按敏感级别分类。
- 传输使用HTTPS/TLS。
- 高敏感字段加密或采用受控密钥服务保护。
- 日志、监控、分析和测试数据脱敏。
- 生产数据不得随意复制到开发和测试环境。
- 建立数据访问审批、审计和异常访问告警。
- 按个人信息保护要求明确处理目的、必要性、告知和保存期限。

### 10.3 文件安全

限制文件类型和大小，进行恶意内容扫描；私有文件通过短时授权链接访问；关键证据文件保留校验摘要和访问记录。删除、替换和下载操作均应遵循权限及留痕规则。

### 10.4 应用与供应链安全

建立依赖漏洞扫描、密钥管理、代码审查、构建产物管理、发布审批和安全补丁流程。支付密钥、短信密钥和云访问密钥不能写入代码仓库或前端包。

## 11. 可观测性、运维与故障处理

### 11.1 日志

结构化日志应包含请求ID、用户/组织内部标识（必要时）、业务对象编号、模块、错误码和耗时。禁止记录明文密码、验证码、完整身份证号、支付密钥和不必要的个人信息。

### 11.2 指标

至少监控API请求量、成功率、错误率和延迟分位数；数据库连接、慢查询、锁等待、复制延迟和磁盘容量；Redis命中率、内存和连接状态；消息堆积、消费失败、死信数量；支付请求成功率、回调延迟、未决交易数量和对账差异；文件上传失败率和对象存储异常；登录失败、异常访问和高风险操作数量。

### 11.3 链路追踪

跨模块和外部服务请求传递统一trace/request ID。对支付创建、回调、退款和对账建立完整链路，能够从业务订单追踪到外部机构交易号。

### 11.4 备份与恢复

- 数据库执行自动备份并定期验证恢复。
- 重要交易数据根据业务目标设置恢复点目标（RPO）和恢复时间目标（RTO）。
- 对象存储开启版本/防误删能力或独立备份策略。
- 备份凭证和生产凭证分离管理。
- 定期开展恢复演练，而不只确认备份任务显示成功。

### 11.5 故障原则

支付机构超时不能直接认定支付失败；应标记未决并查询。消息发送失败不能回滚已经成立的合同事实；应重试通知。缓存不可用时优先降级非关键体验，不得绕过权限和交易校验。外部地图或短信不可用时，应保证核心订单和合同流程可以按预案继续。

## 12. 容量规划：从MVP到100万DAU

100万DAU是长期产品目标。基础设施容量必须基于实际行为数据、峰值系数、接口分布、文件量和读写比例测算，不能把DAU直接换算成服务器台数。

### 12.1 容量估算方法

需要持续采集DAU、MAU、活跃时段和地域分布；每用户每日请求数及关键操作转化率；峰值QPS、并发连接数、接口延迟和读写比例；需求、报价、订单、施工记录和支付的实际写入量；图片/视频平均大小、上传频率、保留周期和下载带宽；消息事件量、通知渠道比例和失败重试量；数据库增长率、索引体积、备份体积和归档需求。

基础估算：
- 日请求量 = DAU × 人均日请求次数。
- 平均QPS = 日请求量 ÷ 86400。
- 峰值QPS = 平均QPS × 实测峰值系数。
- 日文件存储增量 = 日上传文件数 × 平均文件大小。
- 数据库增长量应按业务记录、索引、审计和备份分别测量。

峰值系数不能长期凭经验固定，应通过试运行和真实访问曲线校正。

### 12.2 阶段演进

| 阶段 | 业务目标 | 架构重点 |
|---|---|---|
| MVP / 单城市 | 验证供需、报价、签约、施工和验收闭环 | 模块化单体、单主数据库、Redis、对象存储、基础监控和备份 |
| 增长期 / 多城市 | 提高服务商供给密度和订单履约效率 | 应用水平扩容、读写优化、异步任务、区域检索和运营分析 |
| 规模化 / 多区域 | 承载更高访问量和更复杂工程交易 | 按瓶颈拆分服务、数据库读副本、分区/归档、消息集群和更完善容灾 |
| 全国化 / 多专业 | 多城市、多专业、多主体协作 | 服务治理、跨区域数据策略、专业领域服务、独立风控和数据平台 |

### 12.3 何时采用更复杂的基础设施

- 读流量成为主库瓶颈：先优化SQL、索引和缓存，再评估读副本。
- 单表或单库容量和维护窗口接近上限：评估分区、归档和业务拆分，再决定分库。
- 某些异步任务影响核心接口：将任务处理独立部署。
- 搜索需求超过关系库适用范围：建立搜索索引并设计数据同步。
- 单区域故障影响全国业务：在明确RTO/RPO和预算后规划多可用区或跨区域容灾。
- 团队需要独立交付：在模块边界清晰后逐步服务化。

## 13. 部署与发布架构

MVP建议采用自动化构建和可回滚发布流程：
1. 代码提交触发格式检查、单元测试和静态分析。
2. 构建不可变版本的应用镜像或制品。
3. 执行集成测试和数据库迁移检查。
4. 部署到测试环境验证关键交易链路。
5. 生产发布前进行变更审批和备份确认。
6. 分批或受控发布，观察错误率、延迟和业务指标。
7. 出现异常时回滚应用版本；数据库迁移必须设计兼容性和前向修复方案。

数据库迁移遵循先兼容、后切换、再清理的原则。不能假设应用回滚就能自动回滚已执行的数据结构或交易数据变化。

## 14. 技术选型决策原则

具体框架、云厂商和产品型号在团队能力、预算、目标地区和支付合作方案确定后再选。选型时比较团队熟悉度和招聘可获得性、稳定性和成熟度、长期维护成本、中国大陆网络可达性和数据存储要求、可观测性和备份容灾能力、供应商锁定程度及迁移成本、与电子签约/支付/短信/地图服务的集成成熟度。

避免为了技术潮流同时引入多套数据库、多套消息队列和复杂服务网格。

## 15. MVP实施顺序

1. 工程基础：代码仓库、环境配置、CI/CD、日志、监控、数据库迁移和备份。
2. 身份与主体：用户、个人资料、组织、成员和授权。
3. 供给侧：服务商档案、服务能力、资格审核和服务区域。
4. 需求撮合：服务目录、需求、审核、匹配和邀请。
5. 交易形成：报价版本、合同主体、合同版本和签署证据。
6. 履约闭环：住宅订单、预约、施工记录、变更、验收和整改。
7. 资金链路：支付机构进件、支付、退款、结算状态和对账。
8. 运营售后：投诉、争议、评价、审核和审计。
9. 小范围试点：在单城市、有限服务类目和受控服务商范围内进行真实交易验证。
10. 容量优化：根据真实指标压测和扩容，不提前按百万用户规模采购资源。

## 16. 技术架构待确认事项

正式确定技术方案前，需要确认：
1. 首期客户端采用响应式Web、原生App、跨平台App还是组合方案。
2. 首期云部署区域、云厂商和数据存储要求。
3. 研发团队现有技术栈、人数和运维能力。
4. 支付机构候选名单及其商户进件、退款、结算和对账接口能力。
5. 是否首期接入电子签约、实名认证、地图和短信服务。
6. MVP单城市试点的预计用户量、订单量、图片/视频上传量和预算。
7. 可接受的服务可用性、RPO和RTO目标。
8. 是否需要商业工程模块在MVP阶段上线，还是先保留领域设计、后续启用。

这些决策会影响云资源、部署拓扑和成本，未确认前不应虚构具体服务器配置。
