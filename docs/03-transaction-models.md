# 交易模型设计：住宅服务订单与商业工程项目

> 文档状态：讨论稿 / v0.1
> 更新时间：2026-11-20
> 上游文档：01-business-positioning.md、02-business-model-and-legal-relationships.md
> 本文定义业务模型，不直接规定最终数据库表结构。

## 1. 设计目标

平台有两类核心交易：

- 住宅服务交易：围绕一次明确的安装、维修或局部改造需求，形成相对短周期的服务订单。
- 商业工程交易：围绕工程项目组织多个专业包、合同、施工任务、阶段验收和结算节点，周期更长、参与主体更多。

两类交易共享用户、组织、合同基础能力、支付协作、消息、文件和审计能力，但不应使用同一套核心业务状态机。

设计原则：
1. 先确定交易对象和法律关系，再确定产品流程与数据结构。
2. 需求发布不等于订单成立；报价不等于合同成立；支付成功不等于施工验收完成。
3. 订单、项目、合同、施工任务、支付记录分别建模并关联。
4. 价格、范围、工期和材料变更必须留痕。
5. 施工过程记录应关联具体合同范围和验收节点。
6. 撮合、派单、自营业务应能识别不同责任主体。
7. 资金状态以银行或持牌支付机构的真实交易结果为准。

## 2. 核心业务对象

| 概念 | 定义 | 用途 |
|---|---|---|
| ServiceRequest | 住宅或小型服务需求 | 描述用户需要解决的问题 |
| ServiceOrder | 服务订单 | 管理一次住宅服务交易 |
| Quote | 报价单 | 表达价格、范围、材料和有效期 |
| Project | 商业工程项目 | 管理长期、多参与方工程 |
| ProjectPackage | 工程专业包/标段 | 划分可独立报价或承接的范围 |
| Bid | 项目报名或投标响应 | 记录承包主体参与及报价 |
| Contract | 合同 | 固化签约主体、权利义务和价款 |
| WorkOrder | 施工任务单 | 将合同范围拆成可执行任务 |
| ChangeOrder | 变更单 | 管理范围、价格和工期变化 |
| Acceptance | 验收记录 | 记录阶段或最终验收结果 |
| PaymentRecord | 支付记录 | 关联外部支付机构交易结果 |
| SettlementRecord | 结算记录 | 记录合同价款核算和结算状态 |
| WarrantyCase | 质保/售后案件 | 管理缺陷、返修和售后责任 |

这些是业务概念，不意味着 MVP 必须为每个概念独立建表。

## 3. 住宅服务交易

### 3.1 适用范围

- 新房水电安装。
- 二手房水电改造。
- 水管、电路故障维修。
- 局部线路、管道调整。
- 小型商业空间零星维修（是否纳入住宅服务流程需另行确认）。

核心是一项需求、一个明确服务范围、一组报价与合同，以及一段可追踪的履约过程。复杂需求可以拆成多个订单或合同。

### 3.2 主流程

~~~text
需求草稿
  -> 需求发布
  -> 平台信息完整性检查
  -> 服务商响应与报价
  -> 业主比较并选择
  -> 合同确认与签署
  -> 按合同约定支付
  -> 预约/进场
  -> 施工履约
  -> 变更申请与确认（如有）
  -> 完工申请
  -> 验收
       -> 不通过：整改与复验
       -> 通过：完成
  -> 售后/质保
  -> 关闭
~~~

需求审核只代表信息符合发布规则，不代表平台保证施工质量或工程安全。支付节点由合同和合规支付产品决定；验收操作不等于平台可以自行划转资金。

### 3.3 需求信息

| 信息组 | 内容 |
|---|---|
| 需求类型 | 新装、改造、维修、局部施工 |
| 房屋/场地 | 住宅类型、面积或施工区域、所在城市/区域 |
| 施工范围 | 水路、电路、点位、管线、设备 |
| 现场条件 | 毛坯、已入住、已装修、是否可进场 |
| 现场资料 | 图片、视频、图纸、勘查资料 |
| 时间要求 | 上门时间、计划开工时间、紧急程度 |
| 材料要求 | 业主供料、服务商供料或共同确认 |
| 预算信息 | 可选预算范围，不作为最终成交价 |
| 特殊要求 | 品牌、工艺、隐蔽工程记录、质保要求 |

地址属于需要谨慎处理的个人信息。公开展示时控制精度，仅在合理业务需要和适当授权范围内向候选服务商披露详细地址。

### 3.4 报价模型

报价不能只保存一个总价，建议支持：
- 人工费用。
- 材料费用及品牌、规格。
- 设备或辅材费用。
- 上门、运输或特殊作业费用（如适用）。
- 施工范围和不包含事项。
- 预计工期和报价有效期。
- 付款节点建议。
- 质保承诺及适用条件。

报价方式：
1. 固定总价：范围明确、现场条件相对确定。
2. 清单报价：按点位、长度、数量或项目清单计价。
3. 现场勘查后报价：信息不足时先预约勘查。
4. 工时/服务费报价：适用于部分维修，需明确计费单位和最低收费规则。

报价应有版本。报价调整不能覆盖原记录，业主的选择应明确指向某个报价版本。

### 3.5 需求、订单和合同边界

- ServiceRequest 是需求，不代表双方已建立施工合同。
- ServiceOrder 用于管理进入交易履约阶段的服务。
- Contract 固化真实签约主体和合同条款。
- 一个需求可以有多个服务商报价。
- 如最终由多个独立承包主体分别履约，应拆分合同和责任范围。

建议采用“待签约订单 -> 合同生效 -> 履约中”的阶段划分，避免订单状态与合同法律效力混淆。订单创建、合同签署和合同生效的具体规则需要在后续合同设计中确定。

### 3.6 施工履约与证据

建议记录：
- 预约和进场确认。
- 开工前现场状态。
- 施工人员及所属服务主体。
- 施工日志和阶段进度。
- 隐蔽工程照片/视频及说明。
- 材料进场记录、品牌规格和数量。
- 业主确认事项。
- 变更申请和确认。
- 完工申请。
- 验收问题和整改结果。

文件应记录上传人、时间、关联订单/任务和完整性信息。现场照片可能包含人脸、住址和家庭环境，应设置访问权限、保存期限和导出规则。

### 3.7 验收与售后

验收状态至少区分：
- 待提交验收。
- 待业主确认。
- 验收通过。
- 验收不通过。
- 整改中。
- 待复验。
- 复验通过。
- 部分验收（仅在合同和业务规则允许时）。

验收清单应随业务类型变化，不能把所有维修都套用完整新房水电验收标准。专业标准和强制性规范应由具备相应专业能力的人员核验。

售后记录应包含质保起算时间、范围和排除条件、责任主体、问题证据、响应和处理时间、是否收费及争议情况。

## 4. 商业工程项目交易

### 4.1 为什么使用 Project

商业工程可能包含多个专业施工范围、多家施工企业、多份合同、多批材料采购、多项施工任务、多次工程变更和阶段验收。因此 Project 是项目总容器，不等于一笔服务订单。

### 4.2 项目层级

~~~text
Project（工程项目）
  |
  +-- ProjectPackage（专业包/标段）
  |      |
  |      +-- Bid（报名/投标响应）
  |      +-- Contract（中选后签署的合同）
  |             |
  |             +-- WorkOrder（施工任务）
  |             +-- ChangeOrder（变更/签证）
  |             +-- Acceptance（阶段/最终验收）
  |             +-- PaymentSchedule（合同付款计划）
  |             +-- SettlementRecord（结算记录）
  |             +-- WarrantyCase（质保案件）
  |
  +-- ProjectDocument（项目资料）
  +-- ProjectMilestone（项目里程碑）
~~~

这是推荐层级。简单工程可以只有一个专业包和一份合同；复杂项目可以拆分多个包。

### 4.3 项目发布信息

建议包括：
- 项目名称、类型和所在地区。
- 建设单位/需求方及授权联系人。
- 项目背景、现场条件和施工范围。
- 图纸、技术规范和工程量清单。
- 计划开工、竣工日期和关键节点。
- 报价方式、报名条件和截止时间。
- 资格、资质和人员要求。
- 现场踏勘、答疑和澄清安排。
- 合同主要条件和付款方式。
- 保密要求及项目资料访问范围。

项目资料可能包含商业秘密、建筑图纸和安全敏感信息，应设置项目级权限、访问日志和保密约定。

### 4.4 报名、资格审查与报价

建议流程：
1. 项目公开或定向邀请。
2. 施工主体提交报名资料。
3. 平台进行基础信息完整性检查。
4. 项目发布方或授权人员进行资格审查。
5. 合格主体获取进一步项目资料。
6. 现场踏勘、答疑和澄清。
7. 提交报价及技术响应。
8. 发布方评审、谈判或按适用规则确定合作方。
9. 形成中选结果记录。
10. 双方签署正式工程合同。

平台审核不等于行政许可或资质保证。依法必须招标的项目不得通过普通撮合流程规避法定招标程序。

### 4.5 工程报价结构

支持工程量清单项、单位、工程量、综合单价、合价、人工材料机械构成（按项目需要）、税费口径、暂估价或暂列金额（按合同需要）、报价有效期、工期资源计划、技术方案、偏离说明、不包含事项和报价假设。

报价提交版本、澄清答复和最终确认版本均应保留，不能只保存最终总价。

### 4.6 合同、任务与进度

工程合同应明确：
- 合同双方和授权签署人。
- 承包范围和界面划分。
- 合同价款及计价方式。
- 工期、开竣工条件和里程碑。
- 质量标准和验收流程。
- 安全生产责任和现场管理要求。
- 材料设备品牌、规格及替代流程。
- 变更签证和价款调整机制。
- 进度款申请、审核和支付条件。
- 竣工结算和质保安排。
- 违约责任、索赔和争议解决。

WorkOrder 将合同范围拆成可执行任务。每个任务应有负责人、计划时间、实际时间、工作范围、前置条件、施工记录和验收要求。任务完成不等于合同整体竣工。

### 4.7 变更与签证

变更单应包含提出方、原因、原范围与变更后范围、图纸/清单版本、工程量、价格和税费影响、工期影响、现场证据、审批主体及授权依据、双方确认时间，以及是否形成补充协议。

未按合同约定完成授权审批的变更，不应覆盖原合同价款。系统应区分“已记录”“已审核”和“已形成合同变更”。

### 4.8 阶段验收与结算

验收可包括材料设备进场、隐蔽工程、分项/分部工程、阶段里程碑、竣工验收和缺陷整改复验。

结算可包括预付款（如适用）、进度款、变更签证价款、竣工结算和质保金（按合同约定）。

每笔款项应关联合同条款、申请依据、审核结果和外部支付/结算流水。平台的“审核通过”不代表支付机构已经付款。

## 5. 三种交易组织方式

### 5.1 自主撮合

适用于住宅安装维修为主，也可用于经核验允许采用此类交易方式的企业工程服务采购。

流程：需求发布 -> 服务商响应 -> 报价 -> 需求方比较 -> 选择 -> 合同 -> 履约。

规则：
- 服务商自主决定是否响应。
- 报价和选择记录可追溯。
- 平台可以提供排序和推荐，但应明确推荐规则及商业推广标识。
- 不得伪造报价、成交或评价。

### 5.2 平台派单

适用于标准化程度较高、需要快速响应的维修或小型服务。

流程：需求提交 -> 生成候选服务商 -> 派单邀请 -> 服务商接受/拒绝 -> 确认服务商和计价 -> 合同 -> 履约。

规则：
- 区分“派单邀请”和“已接受订单”。
- 明确服务商拒绝规则和超时机制。
- 记录匹配依据、候选排序和人工干预。
- 派单本身不自动证明或否认劳动关系。
- 若平台统一定价、强制排班并强控制施工，应重新评估经营角色和用工法律风险。

### 5.3 企业工程交易

适用于商业空间、办公楼、酒店、厂房等项目。

流程：项目发布 -> 施工主体报名 -> 资格审查 -> 资料开放 -> 答疑/踏勘 -> 报价 -> 评审 -> 确定合作方 -> 工程合同 -> 施工 -> 变更/验收/进度款/结算 -> 质保。

规则：
- 项目发布方对需求和合同选择承担相应责任。
- 平台不得替代法定招标程序。
- 资质和承包范围按项目类别审查。
- 中选结果与工程合同分开记录。
- 一个项目可产生多份合同和多家承包主体。

## 6. 状态机建议

状态机是业务建议，最终应结合取消、违约和合同规则细化。

### 6.1 住宅服务订单

| 状态 | 含义 |
|---|---|
| DRAFT | 草稿 |
| PUBLISHED | 已发布 |
| MATCHING | 匹配中 |
| QUOTING | 报价中 |
| PENDING_SELECTION | 待选择 |
| PENDING_CONTRACT | 待签约 |
| PENDING_PAYMENT | 待按合同付款 |
| SCHEDULED | 已预约 |
| IN_PROGRESS | 施工中 |
| PENDING_ACCEPTANCE | 待验收 |
| RECTIFICATION | 整改中 |
| COMPLETED | 已完成 |
| AFTER_SALES | 售后中 |
| CLOSED | 已关闭 |
| CANCELLED | 已取消 |
| DISPUTED | 争议处理中 |

支付、退款和结算不应完全依附于订单单一状态，应独立记录。订单取消后仍可能存在退款、争议或售后事项。COMPLETED 与 CLOSED 不应混为一谈。

### 6.2 商业工程项目

| 状态 | 含义 |
|---|---|
| DRAFT | 草稿 |
| PUBLISHED | 已发布 |
| REGISTRATION_OPEN | 报名中 |
| QUALIFICATION_REVIEW | 资格审查中 |
| QUOTATION_OPEN | 报价/响应中 |
| EVALUATION | 评审中 |
| AWARD_PENDING | 待确定合作结果 |
| CONTRACTING | 合同签署中 |
| ACTIVE | 项目执行中 |
| SUSPENDED | 暂停 |
| COMPLETION_PENDING | 待竣工验收 |
| SETTLEMENT | 结算中 |
| WARRANTY | 质保期 |
| CLOSED | 项目关闭 |
| CANCELLED | 项目取消 |
| DISPUTED | 项目争议处理 |

项目状态不能替代专业包、合同、施工任务、验收和支付各自状态。一个项目可处于执行中，而不同专业包处于不同阶段。

### 6.3 独立子流程状态

- Quote：草稿、已提交、已撤回、已过期、已接受、未选中。
- Contract：草稿、待签署、签署中、生效、变更中、已终止、已到期。
- WorkOrder：待开始、待进场、施工中、待验收、整改中、已完成、已取消。
- ChangeOrder：草稿、待审批、已批准、已拒绝、已撤销、已生效。
- Acceptance：待提交、待确认、通过、不通过、整改后复验。
- PaymentRecord：待支付、处理中、成功、失败、关闭、退款处理中、部分退款、已退款。
- SettlementRecord：待申请、审核中、已确认、支付处理中、已结算、存在差异。

外部支付状态应以支付机构通知和查询结果为准，并设计回调验签、幂等处理和对账补偿。

## 7. 异常与边界场景

MVP 规则必须覆盖：
1. 无人报价：延长响应期、调整范围或人工协助，不得伪造供给。
2. 服务商拒单/超时：释放邀请并继续匹配。
3. 报价过期：重新确认价格，不自动沿用。
4. 现场条件与描述不符：勘查并形成范围/价格变更。
5. 业主取消：按合同和实际履约情况处理费用。
6. 服务商违约：按合同处理替换、退款或其他救济。
7. 部分完工：按合同处理部分验收和价款，不强行标记整体完成。
8. 验收不通过：记录问题、整改期限和复验结果。
9. 施工损坏或安全事故：保留证据并启动责任和保险处理。
10. 材料缺货或替代：经约定主体确认规格、价格和质量变化。
11. 合同变更：保留原版本和补充协议。
12. 支付超时或重复回调：通过幂等和主动查询防止重复入账。
13. 退款失败：进入人工处理和对账差异队列。
14. 争议款项：遵循合同和支付机构规则，不由平台擅自冻结或划拨。
15. 商户退出或资质失效：限制新交易，妥善处理存量合同和售后。

## 8. 金额一致性

每笔交易至少应追踪：
- 报价金额及版本。
- 合同金额及版本。
- 已确认变更金额。
- 当前合同应付金额。
- 付款申请金额。
- 外部支付成功金额。
- 已退款金额。
- 已结算金额。
- 未结算差额及原因。

不能只维护一个可随意覆盖的订单金额。金额变化必须关联报价、合同或变更依据，并记录币种、税费口径、精度和舍入规则。

平台服务费单独计算并记录合同依据和外部收款结果。第三方施工价款不得直接记作平台自身服务收入。

## 9. MVP 范围建议

### 首期必须有
- 住宅需求发布。
- 服务商资料和基本核验。
- 自主报价与业主选择。
- 订单和合同关联。
- 施工预约、进度记录和图片留痕。
- 完工申请、验收、整改和复验。
- 售后/投诉入口。
- 外部支付交易记录关联、退款记录和对账能力（具体支付产品待机构确认）。
- 平台运营审核和异常处理。

### 后续加入
- 自动派单与复杂匹配。
- 多服务商拆单。
- 复杂材料清单和供应链交易。
- 商业工程完整报名、评审和投标工作流。
- 工程量清单、变更签证、进度款和竣工结算。
- 企业 SaaS 深度功能。

### MVP 暂不建设
- 平台自有资金池和可划转钱包。
- 未经支付机构确认的担保交易或资金冻结。
- 复杂工程项目招投标替代系统。
- 无真实业务验证的全行业通用工作流。
- 为长期 DAU 目标提前拆分大量微服务。

## 10. 待确认业务决策

| 决策项 | 推荐初值 | 原因 |
|---|---|---|
| 住宅首期品类 | 安装、维修、局部改造 | 决定需求字段和验收模板 |
| 首期报价 | 明细报价 + 现场勘查后报价 | 降低信息不足导致的价格争议 |
| 服务商选择 | 自主报价优先 | 先验证真实供需和转化 |
| 派单 | 后续增加 | 需验证匹配质量及平台责任边界 |
| 住宅拆单 | MVP 原则上一个主要服务主体 | 降低多方合同和责任复杂度 |
| 商业工程 | 先发布、报名和撮合，再扩展执行 | 工程流程复杂、合规要求高 |
| 项目专业包 | 支持一个或多个 | 适配项目规模差异 |
| 支付 | 先确认机构产品与资金路径 | 防止先开发后发现资金模式不可用 |
| 材料 | 首期作为报价明细/供应商信息 | 区分材料销售主体和平台角色 |
