# 可观测性、生产运维与容量管理规范

> 状态：建议方案 / v0.1，待技术选型、SRE评审和压测验证  
> 更新时间：2026-11-20  
> 适用范围：全部业务微服务、市场情报采集系统、数据平台、API网关、消息系统、数据库、缓存、对象存储及运行基础设施  
> 上游文档：08 技术架构、10 MVP实施路线图、13 微服务系统架构设计、14 微服务边界与API接口契约、15 事件驱动架构与消息协作规范、16 平台安全架构与安全治理规范

## 1. 目标与基本原则

本规范建立生产系统的可观测性、服务等级目标、告警、发布、容量规划、故障处置、备份恢复和运维治理基线。

目标不是单纯收集日志，而是回答：
- 用户是否能够正常发布需求、报价、签约、履约、验收和付款？
- 哪个服务、依赖或基础设施导致故障？
- 故障影响哪些用户、订单、城市和交易环节？
- 当前容量能否承受流量增长和突发峰值？
- 发布是否安全，出现问题能否快速回滚？
- 数据和文件是否可以恢复，恢复后业务状态是否一致？

基本原则：
1. 以用户可感知的业务结果衡量服务质量，不只看机器CPU。
2. 日志、指标、链路追踪和业务审计互相补充，不互相替代。
3. 交易核心链路与市场采集、文档解析、离线分析隔离资源。
4. 告警必须对应责任人、处置手册和升级路径。
5. 所有容量结论必须来自可复现的压测或生产观测，不以DAU直接推算服务器数量。
6. 生产变更可追踪、可回滚；数据库变更优先采用向前兼容的渐进式迁移。
7. 备份成功不等于恢复成功，必须定期演练。
8. 先建立最小可用运维能力，再按规模引入复杂平台。

## 2. 生产系统分层

建议按以下层次采集信号：

| 层次 | 监控对象 | 典型信号 |
|---|---|---|
| 用户体验 | Web、App、开放API | 页面可用性、关键操作成功率、首屏和接口延迟 |
| 业务流程 | 需求、报价、合同、订单、支付、售后 | 转化、失败、积压、超时和状态异常 |
| 服务应用 | 微服务、Worker、Gateway | 请求量、延迟、错误率、线程池、连接池 |
| 异步处理 | 消息队列、Outbox、Inbox、定时任务 | 积压、最老消息年龄、消费失败、重试 |
| 数据层 | MySQL、缓存、搜索、对象存储 | 查询延迟、锁等待、连接、命中率、容量 |
| 基础设施 | 容器、节点、网络、磁盘 | CPU、内存、磁盘、网络、重启和资源限制 |
| 第三方依赖 | 支付机构、短信、地图、电子签署、数据源 | 可用性、响应时间、错误码、限频和费用 |

每个服务必须有服务目录条目：服务名称、业务负责人、技术负责人、运行环境、依赖关系、数据所有权、SLO、告警渠道、值班方式、部署方式和恢复手册。

## 3. 四类核心可观测信号

### 3.1 结构化日志

应用日志采用结构化格式，建议JSON。统一字段至少包括：
- timestamp：事件时间，统一时区和时间同步策略。
- level：DEBUG / INFO / WARN / ERROR。
- service、serviceVersion、environment。
- traceId、spanId、requestId。
- userId、organizationId仅在必要且符合隐私策略时使用内部标识，不记录凭据。
- operation、resourceType、resourceId（按敏感级别脱敏）。
- result、errorCode、durationMs。
- message：可检索的简短说明。

日志规则：
- 生产默认不长期启用高量DEBUG日志。
- 不记录密码、验证码、访问令牌、刷新令牌、密钥、支付签名原文、完整身份证件和不必要的个人信息。
- 错误日志应包含错误码和关联ID，不应只输出无法定位的“系统异常”。
- 同一异常避免在每层重复打印完整堆栈；由边界层记录必要上下文。
- 访问日志与业务审计日志分离。
- 记录采样策略、保留期限、访问权限和删除策略。
- 日志系统不可用时，应用应有有界缓冲和降级策略，不能无限占用磁盘或阻塞交易线程。

### 3.2 指标 Metrics

指标使用统一命名、单位和标签规范。避免将userId、orderId、手机号等高基数字段作为指标标签。

通用服务指标：
- 请求数、成功数、错误数。
- 请求延迟P50/P90/P95/P99。
- 当前并发请求、队列长度。
- JVM/运行时堆、GC、线程、协程或事件循环状态。
- 数据库连接池活跃/空闲/等待数。
- 缓存命中率、超时和错误。
- 服务重启、容器OOM和健康检查失败。

业务指标：
- 需求创建/发布成功率。
- 报价提交成功率、有效报价覆盖率。
- 合同签署完成率。
- 订单创建、开工、完工、验收成功率。
- 支付意图创建、支付机构确认、退款确认和对账差异。
- 售后工单积压、超时和解决时长。
- 市场采集任务成功率、来源限频、解析失败和人工审核积压。

所有业务指标应绑定明确口径：分子、分母、统计窗口、去重规则、排除条件、数据来源和责任人。业务指标不可仅由前端埋点计算，关键交易事实应以服务端业务事件为准。

### 3.3 分布式链路追踪

采用兼容W3C Trace Context的追踪传播方式，贯通：
客户端/网关 → 业务服务 → 下游服务 → 数据库/缓存/消息系统 → 异步消费者 → 第三方接口。

要求：
- 网关生成或校验trace上下文，内部调用继续传播。
- 异步消息携带traceparent、correlationId和causationId。
- 一个业务流程可以包含多个Trace，但必须有稳定业务关联ID。
- Span记录服务、操作、耗时、结果和必要错误信息。
- 不把完整请求体、合同内容、支付凭据和个人信息写入Span属性。
- 对高流量成功请求采样，对错误和高延迟请求提高采样概率；采样规则需保护关键交易问题的排查能力。
- Trace保留期限与成本按系统规模和合规要求配置。

### 3.4 前端真实用户监控

采集页面加载、资源失败、JS异常、关键API耗时和关键操作结果。前端监控必须：
- 对用户标识进行去标识化。
- 不采集输入框内容、密码、支付信息和现场照片内容。
- 区分网络错误、服务端错误、用户取消和业务规则拒绝。
- 将关键操作与服务端requestId/traceId关联。
- 允许用户隐私设置和适用法规要求优先于分析采集。

## 4. SLI、SLO与SLA

SLI是实际测量指标；SLO是内部服务目标；SLA是对客户或合作方的正式服务承诺。三者不可混用。MVP阶段先建立SLI和内部SLO，经过生产数据验证后再对外承诺SLA。

建议初始内部SLO方向（目标值须由试运行基线、业务风险和成本评审确定）：

| 服务/流程 | SLI | 目标定义方式 |
|---|---|---|
| 公共API | 成功请求比例 | 排除明确业务拒绝、客户端取消和约定不计入项后计算 |
| 需求发布 | 发布成功率、端到端耗时 | 从提交到权威服务确认成功 |
| 报价提交 | 提交成功率、P95延迟 | 以服务端持久化结果为准 |
| 合同服务 | 签署状态处理延迟 | 区分签署方操作时间和平台处理时间 |
| 订单服务 | 关键状态转换成功率 | 按合法状态机转换统计 |
| 支付服务 | 回调处理及时率、状态确认率 | 支付机构确认和平台处理分开计算 |
| 消息系统 | 最老消息年龄、消费成功率 | 按主题重要性分别设置 |
| 市场采集 | 任务完成率、来源成功率 | 按来源、连接器和采集窗口分别计算 |

建议用滚动窗口计算可用性和错误预算。关键交易服务可以采用较短窗口监控突发故障、较长窗口评估稳定性。不得用全平台平均值掩盖支付或合同服务单点恶化。

SLO设计必须明确：
- 统计对象和请求分类。
- 成功/失败定义。
- 排除条件和维护窗口。
- 统计窗口和数据源。
- 目标值及目标生效日期。
- 预算消耗速度和发布策略。
- 责任团队及例外审批。

## 5. 告警体系

### 5.1 告警分级

| 级别 | 含义 | 处理要求 |
|---|---|---|
| P0 | 核心交易大面积不可用、资金/数据安全重大风险 | 立即响应，启动事件指挥和业务止损 |
| P1 | 核心业务重要功能显著降级或关键数据处理异常 | 立即通知责任人，快速缓解 |
| P2 | 单服务或非核心能力故障，有可行绕行方案 | 按值班SLA处理 |
| P3 | 容量趋势、质量退化或一般异常 | 进入工作时间处理和问题跟踪 |

具体响应时限应结合团队规模和是否提供7×24服务另行批准，不在没有值班能力时虚构全天候承诺。

### 5.2 告警规则

告警优先基于用户影响和持续时间，避免单点瞬时毛刺触发大量噪声。

核心告警：
- 关键API错误率持续超过阈值。
- 关键交易流程成功率明显下降。
- P95/P99延迟持续恶化。
- 支付回调验签失败、支付状态长时间待确认或对账差异激增。
- Outbox积压和最老事件年龄超过业务容忍窗口。
- 合同、订单、退款等关键事件进入死信。
- 数据库连接池耗尽、锁等待、复制延迟或磁盘空间不足。
- 容器频繁重启、OOM、节点不可调度。
- 对象存储访问失败或文件扫描积压。
- 备份失败、恢复验证失败。
- 市场采集违反来源限频、来源授权到期或任务异常激增。

每条告警必须配置：
- 告警名称、严重级别和触发条件。
- 影响服务和业务流程。
- 值班责任人和升级联系人。
- 排查链接、Dashboard和Runbook。
- 临时缓解措施和禁止操作。
- 恢复条件及事后复盘要求。

### 5.3 告警降噪

- 同一根因告警聚合，避免每个实例分别通知。
- 维护窗口和计划发布应有明确静默机制，但不得静默安全和资金风险告警。
- 使用持续时间、错误预算消耗速度和多信号关联减少误报。
- 告警恢复后自动关闭或进入待确认状态。
- 定期统计误报、漏报、无人认领和重复告警。

## 6. Dashboard设计

至少建设以下仪表盘：

1. **业务健康总览**：需求、报价、合同、订单、验收、支付、退款和售后漏斗。
2. **交易核心服务**：各服务请求量、错误率、延迟、依赖和资源。
3. **支付与资金核对**：支付意图、机构确认、回调、退款、对账差异和待确认交易。
4. **异步消息**：主题积压、最老消息、Outbox、Inbox、重试、死信和消费者状态。
5. **数据基础设施**：数据库、缓存、搜索、对象存储、备份和容量。
6. **市场情报系统**：来源健康、采集任务、限频、解析、实体审核和城市数据新鲜度。
7. **安全运维**：登录异常、授权拒绝、敏感导出、密钥轮换和安全事件。
8. **成本与容量**：计算、存储、网络、日志、追踪、第三方API和单位业务成本。

Dashboard应展示指标定义、时间窗口、数据更新时间和数据质量提示。业务指标应能下钻到具体服务和事件，但不得让普通运营人员因此获得超出岗位权限的个人信息。

## 7. 发布与环境治理

### 7.1 环境隔离

至少区分：
- local：开发者本地环境。
- dev：集成开发环境。
- staging：预发布验证环境。
- production：生产环境。

环境之间数据库、对象存储桶、消息主题、密钥、支付配置和用户数据严格隔离。测试支付必须使用支付机构提供的沙箱或明确的测试环境，禁止误用生产商户配置。

### 7.2 CI/CD流水线

建议流程：

~~~text
提交代码
  -> 格式/静态检查
  -> 单元测试
  -> 服务集成测试
  -> API与事件契约测试
  -> 安全与依赖扫描
  -> 构建不可变制品
  -> 镜像/制品签名与登记
  -> Staging部署
  -> 冒烟/回归/迁移验证
  -> 审批
  -> Production灰度发布
  -> 健康检查与业务指标观察
  -> 扩大流量或自动/人工回滚
~~~

生产部署必须可追溯到代码提交、构建流水线、制品摘要、配置版本、操作者和审批记录。禁止在生产容器内手工修改代码或依赖作为常规发布方式。

### 7.3 发布策略

按服务风险选择：
- 滚动发布：适用于兼容性良好的无状态服务。
- 金丝雀发布：先让少量流量进入新版本，观察错误率和延迟。
- 蓝绿发布：需要快速切换且环境资源允许时使用。
- 功能开关：用于分阶段启用高风险功能，但开关变更也必须审计。

发布前确认健康检查、容量余量、数据库兼容性、消息契约兼容性和回滚路径。发布后观察关键业务SLI，不只看容器是否启动成功。

### 7.4 数据库迁移

采用Expand-Migrate-Contract：
1. Expand：先增加兼容字段/表/索引，不破坏旧版本。
2. Migrate：分批回填并校验数据。
3. Switch：应用逐步切换读写逻辑。
4. Contract：确认所有实例和消费者不再依赖旧结构后，再删除旧字段。

大表迁移应评估锁、IO、复制延迟和回滚方案。不可逆数据迁移必须有备份、校验和人工审批。应用回滚不意味着数据库结构可以直接回滚。

## 8. 容量规划：从100万DAU目标推导

100万DAU是规划目标，不是当前生产事实，也不能直接换算为固定服务器数量。容量必须从用户行为、请求分布、峰值系数、缓存命中、异步任务和第三方依赖推导。

### 8.1 容量模型输入

| 参数 | 说明 | 获取方式 |
|---|---|---|
| DAU | 日活跃用户数 | 真实用户行为统计 |
| sessions/user/day | 每活跃用户每日会话数 | 埋点和服务端会话 |
| requests/session | 每会话请求数 | API访问日志 |
| peak factor | 峰值相对日均流量系数 | 生产分钟级流量曲线 |
| write ratio | 写请求占比 | API和数据库统计 |
| cache hit ratio | 缓存命中率 | 缓存指标 |
| async ratio | 转为异步处理的任务比例 | 消息生产与消费指标 |
| payload size | 请求/响应和消息平均体积 | 线上采样 |
| third-party ratio | 需要外部服务的请求比例 | 依赖调用统计 |

估算公式：

```
日请求量 = DAU × sessions/user/day × requests/session

日均RPS = 日请求量 ÷ 86,400

峰值RPS = 日均RPS × peak factor

峰值写RPS = 峰值RPS × write ratio
```

以上公式只用于初步建模。真实容量还受请求复杂度、热点资源、数据库事务、文件流量和后台任务影响。

### 8.2 示例情景（仅用于演示计算方法）

假设100万DAU，每人每天2次会话，每次会话产生20次服务端请求：

- 日请求量：40,000,000次。
- 日均RPS：约463次/秒。
- 若假设峰值系数为5，峰值约2,315次/秒。

这不是平台实际预测值，也不是服务器采购结论。用户行为、请求计数边界和峰值系数均需用试运营数据校准。若一次页面访问触发多个API，必须明确按HTTP请求、业务操作还是页面会话计数。

### 8.3 按业务域分解

分别计算：
- 用户身份和组织服务。
- 需求与搜索服务。
- 匹配与报价服务。
- 合同与电子签署集成。
- 履约订单与项目进度。
- 支付、退款和对账。
- 售后、争议和通知。
- 市场采集、解析和城市分析。

市场采集吞吐与交易API吞吐不能混成一个平均值。采集系统通常受来源限频、任务调度和解析资源约束；交易系统则更关注交互延迟、事务一致性和峰值并发。

### 8.4 容量安全余量

容量规划应同时考虑：
- 正常峰值下的CPU、内存、连接池和磁盘余量。
- 单实例/单节点故障后的剩余承载能力。
- 数据库连接和慢查询瓶颈。
- 消息积压时的恢复吞吐。
- 第三方支付、短信和电子签署的配额。
- 日志、追踪和对象存储的增长。
- 大促、极端天气、区域性施工旺季等业务突发（如适用）。

安全余量应通过压测和故障演练确定，不设置脱离实际架构的统一百分比。

## 9. 压测与性能验收

### 9.1 压测类型

- 基准测试：测量正常负载下延迟和资源消耗。
- 负载测试：验证预期峰值和持续负载。
- 压力测试：逐步增加负载，识别性能拐点和失效边界。
- 尖峰测试：模拟短时间突发流量。
- 耐久测试：持续运行，发现内存泄漏、连接泄漏和队列积压。
- 故障注入：模拟实例退出、数据库切换、消息系统不可用和第三方超时。
- 恢复测试：验证故障后积压能否在目标时间内消化。

### 9.2 业务场景

压测不能只打一个空接口，应模拟真实业务读写比例和依赖：
- 注册/登录、组织切换。
- 浏览服务目录和城市服务商。
- 创建和发布需求。
- 匹配服务商、邀请报价。
- 提交和接受报价。
- 合同创建和签署状态回调。
- 订单开工、进度更新、完工申请和验收。
- 支付意图、支付机构回调模拟、退款和对账。
- 售后工单创建与状态更新。
- 市场采集任务、网页解析和实体去重。

真实支付和真实短信不得用于无控制的压测。使用沙箱、模拟依赖或专门压测环境。

### 9.3 验收记录

每次压测保存：
- 代码版本、镜像摘要和配置版本。
- 环境拓扑、数据库规模和数据分布。
- 测试脚本版本、场景和请求比例。
- 并发用户、到达率、持续时间和峰值曲线。
- P50/P95/P99延迟、错误率、吞吐和资源曲线。
- 数据库慢查询、锁等待、连接池和消息积压。
- 第三方模拟参数。
- 瓶颈、修复项、复测结果和结论。

压测报告必须注明测试环境与生产环境差异。未完成瓶颈分析和错误率核对，不得只以“达到某个RPS”宣布通过。

## 10. 弹性伸缩与过载保护

- 无状态API服务可按CPU、请求并发、延迟或自定义业务指标扩缩容。
- Worker按队列积压和最老消息年龄扩缩容，同时受下游限流约束。
- 数据库不能简单通过增加应用实例解决；先评估查询、索引、连接池和事务设计。
- 对第三方服务设置超时、并发上限、熔断和隔离舱。
- 对非核心功能采用降级，例如延迟推荐、暂停非紧急分析、降低非必要埋点。
- 对核心交易操作禁止静默丢弃；无法处理时明确返回可重试状态并保证幂等。
- 采用背压机制限制任务生产速度，防止队列无限增长。
- 扩容策略必须考虑冷启动、连接风暴和缓存击穿。

## 11. 数据库、缓存和消息运维

### 11.1 数据库

监控连接数、慢查询、事务时长、锁等待、死锁、磁盘、IOPS、复制延迟和备份状态。建立慢查询治理、索引评审、连接池配置、容量预警和变更审批流程。

交易核心数据库优先保障事务正确性和恢复能力。读写分离、分库分表和多活架构应在数据规模与瓶颈证据充分后引入，不作为MVP默认复杂度。

### 11.2 缓存

缓存不是权威业务数据源。明确缓存键、TTL、失效策略和一致性要求。对热点Key、缓存雪崩、穿透和击穿设置保护。缓存故障时，数据库应有过载保护，不能让所有请求直接穿透。

### 11.3 消息系统

依照文档15监控Outbox、Inbox、主题积压、最老消息年龄、消费延迟、重试和死信。扩容消费者时确认分区数、下游数据库能力和幂等正确性。不得为清空积压而无限增加消费者并压垮下游。

## 12. 备份、灾难恢复与业务连续性

### 12.1 备份对象

- 交易数据库及必要的时间点恢复日志。
- 合同、验收证据和业务附件。
- 服务配置、基础设施配置和密钥恢复材料（按安全策略）。
- 事件Schema、部署清单和必要审计数据。
- 市场研究原始资料及规范化数据（按来源授权和保留策略）。

### 12.2 RPO与RTO

- RPO：可接受的数据恢复点损失窗口。
- RTO：从故障发生到恢复业务服务的目标时间。

应按业务重要性分别设定目标，不为所有系统套用同一个数字。支付、合同和订单的恢复还必须进行外部支付机构状态核验、消息补偿和数据对账。

### 12.3 恢复演练

至少验证：
1. 数据库备份可恢复。
2. 对象存储文件与数据库引用一致。
3. 应用配置和密钥可按授权恢复。
4. 消息积压可以安全重放。
5. 支付状态可通过机构查询和对账恢复。
6. 恢复后的业务状态机无非法跳转。
7. 关键用户流程能够端到端执行。

备份任务成功率不是恢复能力指标；只有完成恢复演练并验证业务正确性才算通过。

## 13. 运维组织与变更管理

每个生产服务明确：
- 产品负责人：确认业务影响和优先级。
- 服务技术负责人：负责服务质量、容量和技术恢复。
- 运维/SRE责任人：负责平台、发布、监控和基础设施。
- 安全负责人：负责安全事件和高风险变更。
- 财务/支付负责人：负责支付异常、退款和对账流程。

团队规模较小时可以一人承担多个职责，但高危操作的申请、审批和执行应尽可能分离。

变更分级：
- 常规变更：已验证、可回滚的常规发布。
- 高风险变更：数据库结构、支付配置、身份权限、消息契约和核心路由变更。
- 紧急变更：为止损或恢复服务执行，事后补齐审批和复盘。

所有变更记录范围、原因、风险、测试、审批、实施人、结果和回滚方案。

## 14. 故障处理Runbook模板

每个P0/P1告警至少有对应Runbook，包含：
1. 告警现象和业务影响。
2. 首要检查Dashboard和日志查询。
3. 关联服务、依赖和近期发布。
4. 安全的止损动作。
5. 明确禁止的高风险操作。
6. 回滚或降级步骤。
7. 数据修复和对账步骤。
8. 恢复验证清单。
9. 升级联系人和沟通模板。
10. 复盘所需证据。

故障处理优先保护数据和资金正确性。不得通过直接修改支付状态、删除消息或绕过状态机来快速“恢复绿色”。

## 15. 事故复盘

P0/P1和重复发生的P2故障应进行复盘。复盘聚焦系统性原因，不以单纯追责替代改进。

复盘至少包含：
- 时间线和发现方式。
- 受影响用户、组织、城市、订单和交易范围。
- 影响持续时间和业务损失评估。
- 根因、促成因素和未能及时发现的原因。
- 止损、恢复和数据核对过程。
- 监控、测试、架构、流程和权限方面的改进项。
- 每项改进的责任人、截止日期和验证方式。

## 16. MVP阶段实施顺序

### 第一阶段：上线前基础能力
- 服务健康检查和结构化日志。
- API请求量、错误率、延迟和基础资源监控。
- requestId/traceId贯通关键调用。
- 数据库、缓存和消息积压基础监控。
- 需求、报价、合同、订单、支付关键业务指标。
- 生产发布审批、制品版本记录和回滚手册。
- 数据库及文件备份，完成至少一次恢复验证。
- P0/P1告警责任人和Runbook。

### 第二阶段：试运营稳定性
- 引入集中日志、指标平台和分布式追踪。
- 建立服务目录、SLO和错误预算。
- 交易与采集资源隔离。
- 建立压测基线、慢查询治理和容量趋势。
- 完善灰度发布、自动化回归和故障演练。

### 第三阶段：多城市和规模化
- 依据真实负载进行服务级弹性伸缩。
- 建立多可用区/多地域恢复策略（按业务必要性）。
- 细化成本分摊、单位订单基础设施成本。
- 建立更完善的值班、事故指挥和供应商SLA管理。
- 通过连续压测和容量预测支持增长决策。

## 17. 上线验收清单

- [ ] 每个生产服务有业务和技术负责人。
- [ ] 核心API具备请求量、延迟和错误率监控。
- [ ] 关键交易流程具备服务端业务成功率指标。
- [ ] Trace可贯通网关、服务和异步消费者。
- [ ] 日志无密码、令牌、密钥和不必要敏感信息。
- [ ] 支付待确认、回调异常和对账差异有独立告警。
- [ ] Outbox积压、死信和消费者延迟有告警。
- [ ] 市场采集任务与交易服务有资源隔离。
- [ ] 生产发布具备审批、制品追溯和回滚方案。
- [ ] 数据库迁移具备兼容性和恢复策略。
- [ ] 完成关键业务场景压测并形成报告。
- [ ] 完成数据库和文件恢复演练。
- [ ] P0/P1告警有Runbook和责任人。
- [ ] 安全事件和业务事故有应急流程。

## 18. 待确认事项

- 最终日志、指标、追踪平台和部署形态。
- SLI/SLO初始目标值及对外SLA边界。
- 是否提供7×24值班以及响应承诺。
- 生产环境可用区和灾备部署策略。
- 数据库备份频率、时间点恢复能力和保留期限。
- 各业务域RPO/RTO。
- 100万DAU的用户行为模型、峰值系数和业务读写比例。
- 压测环境与生产环境的资源比例和数据规模。
- 各服务扩缩容指标、最小副本数和过载降级策略。
- 日志、指标和Trace的留存周期及预算。
- 第三方服务配额、故障通知和合同SLA。

**结论：** 生产运维能力应围绕业务可用性、交易正确性、故障可定位、容量可验证和数据可恢复建立。100万DAU目标需要通过用户行为模型、分业务域压测和真实生产指标逐步校准，不能直接转化为固定机器规格或服务数量。
