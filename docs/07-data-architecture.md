# 数据架构与领域模型

> 文档状态：讨论稿 / v0.1  
> 更新时间：2026-11-20  
> 适用范围：中国大陆水电安装服务与工程交易平台  
> 上游文档：01 商业定位、02 商业模式与法律主体关系、03 交易模型、04 支付与结算合规、05 产品架构、06 业务规则与流程  
> 本文目标：确定核心业务领域、实体边界、对象关系、数据归属和一致性原则。本阶段不直接生成数据库DDL，也不把领域对象机械地等同于数据库表。

## 1. 数据架构目标

平台数据架构必须支持：
- 个人用户与经营组织并存，同一用户可以具有多种业务身份。
- 住宅服务订单和商业工程项目采用不同业务模型。
- 需求、报价、合同、订单、履约、验收、售后形成可追溯交易链。
- 合同签约主体、实际履约主体、收款权利主体和支付商户可以存在差异，但必须显式表达并校验。
- 支付、退款、结算以合作银行或持牌支付机构的外部交易事实为准。
- 关键业务对象支持版本管理、操作审计和证据留存。
- 首期按单城市业务规模建设，同时为多城市、多组织、多服务类目和全国化扩展预留边界。
- 后续能够扩展材料供应链、施工设备租赁、暖通、消防、弱电和机电安装。

不以“预估100万DAU”为由提前拆成大量微服务或复杂分库。先保证业务语义正确、数据关系清晰和关键交易一致性。

## 2. 领域边界总览

| 领域 | 核心职责 | 主要对象 |
|---|---|---|
| 身份与访问 | 用户身份、认证、登录和权限 | User、PersonProfile、Credential、Role、Permission |
| 组织与经营主体 | 企业/个体经营主体及成员关系 | Organization、OrganizationMember、BusinessProfile |
| 服务商中心 | 服务能力、准入、区域和证照 | ProviderProfile、ServiceCapability、Qualification |
| 服务目录 | 服务类目、计价属性和验收参考 | ServiceCategory、ServiceItem、RequirementSchema |
| 地理与区域 | 行政区划、服务范围和地址 | Region、ServiceArea、Address |
| 需求与撮合 | 需求发布、审核、邀请和匹配 | Demand、Match、Invitation |
| 报价 | 服务商报价及版本 | Quotation、QuotationVersion、QuotationLine |
| 合同 | 合同主体、条款、版本和变更 | Contract、ContractVersion、ContractParty、ContractChange |
| 住宅履约 | 住宅订单、预约、施工和验收 | ServiceOrder、Schedule、WorkLog、Acceptance |
| 商业工程 | 工程项目、专业包、进度和结算 | Project、ProjectPackage、ProjectContract、ProgressClaim |
| 材料供应链 | 材料目录、供应商、采购和交付 | Product、Supplier、PurchaseOrder、Delivery |
| 交易资金 | 付款请求、支付流水、退款、结算和对账 | PaymentPlan、PaymentIntent、PaymentTransaction、Refund、Settlement |
| 售后与争议 | 投诉、工单、争议和质保 | AfterSalesCase、Complaint、Dispute、WarrantyObligation |
| 评价与信用 | 交易评价、履约指标和信用事件 | Review、RatingAggregate、CreditEvent |
| 消息与文件 | 消息通知、附件和证据 | Message、Notification、FileAsset、Evidence |
| 运营与风控 | 审核、规则、处罚和风险事件 | ReviewTask、RiskCase、RuleVersion |
| 审计与分析 | 操作记录和分析事件 | AuditEvent、BusinessEvent、MetricSnapshot |

领域边界是业务责任边界，不代表首期必须部署为独立服务。MVP可以采用模块化单体，在代码模块和数据访问层保持边界。

## 3. 身份、个人与组织模型

### 3.1 User：平台账户

User表示平台登录账户，是身份和权限体系的入口，不等于经营主体，也不等于某笔交易中的合同主体。用户可关联一个或多个登录凭证、个人身份资料、组织成员关系，以及作为业主、服务人员、负责人、项目经理等交易参与角色的记录。

账户状态与经营主体状态分开管理。账户冻结不应删除其历史合同、订单和审计记录。

### 3.2 PersonProfile：个人资料

个人资料承载自然人基础信息和经过核验的信息。身份证件等敏感信息应独立控制访问权限，采用最小必要采集、脱敏展示、加密存储和访问审计。身份证号码、手机号等敏感字段不应直接用作业务表主键或对外公开标识。

### 3.3 Organization：组织/经营主体

Organization表示企业、个体工商户或其他经平台识别的组织主体。建议记录组织类型、登记名称和展示名称、统一社会信用代码或适用登记标识、登记状态和核验状态、登记代表人/经营者信息（按必要范围采集）、注册地和经营地址、主体有效期及核验时间、主体变更历史。

平台内部组织类型不能直接替代法律上的主体类型判断。

### 3.4 OrganizationMember：组织成员关系

用户与组织通过成员关系建立连接。成员关系至少包含组织ID、用户ID、成员状态、组织内角色、权限范围、授权起止时间，以及邀请、接受、撤销和变更记录。

角色可以包括法人/经营者、管理员、财务、项目经理、报价人员、现场负责人和普通施工成员。角色只是权限模板；关键签约和资金动作仍应校验具体授权。

### 3.5 BusinessProfile：经营身份资料

个人或组织可建立经营资料，用于说明经营类型、业务范围、服务类目和对外展示信息。BusinessProfile不能替代营业执照、行政许可、资质证书或支付机构商户审核。

### 3.6 交易参与身份快照

每笔关键交易在报价、签约和履约节点，应保存参与方身份快照：当时的个人或组织主体、组织成员及授权关系、展示的主体名称和必要登记信息、合同签署人及授权依据、实际履约主体、收款权利主体。

后续组织名称、成员或权限变化，不应改写历史交易当时的主体事实。

## 4. 服务商、能力与准入模型

### 4.1 ProviderProfile

ProviderProfile表示可参与平台服务交易的服务提供者资料。服务提供者可以关联自然人或组织，但必须明确经营主体和履约关系。

应将平台服务商档案与法律经营主体分开：
- ProviderProfile负责服务展示、接单状态、能力和服务表现。
- PersonProfile/Organization负责身份及主体信息。
- ContractParty负责具体合同中的签约身份。
- MerchantAccount负责支付机构侧商户身份映射。

### 4.2 ServiceCapability

记录服务商可以提供的服务类目、服务区域、可承接工作类型、计价方式和能力说明。能力状态应按类目和区域控制，不能用一个总状态代表所有服务范围。

### 4.3 Qualification

记录证照/资格材料及核验结果，包括证照类型、编号和发证主体、适用主体、适用业务范围、有效期、原始文件引用、核验状态、核验人和核验时间，以及失效、撤销、变更和复核记录。

“技能证明”“培训经历”“平台能力审核”和“依法要求的行政许可/资质”必须区分字段和展示文案。

### 4.4 ProviderAvailability

记录服务商可接单状态、可服务时段、当前容量和临时停接状态。排期数据不能替代合同承诺；接单容量也应允许人工调整并记录原因。

## 5. 服务目录与区域模型

### 5.1 服务目录

ServiceCategory用于构建层级类目，例如住宅水电安装下的新房水电安装、局部水电改造、水路维修、电路维修、厨卫水电安装；商业水电工程下的商业空间给排水、商业空间电气安装及其他经审核开放的专业类目。

ServiceItem描述更具体的服务项目、单位和计价属性。类目层级和项目明细应支持版本化，避免历史订单随目录修改而改变含义。

### 5.2 RequirementSchema

不同服务类目具有不同需求采集字段。RequirementSchema定义字段、必填规则、校验规则和版本。Demand保存提交时的字段值快照，不能只引用当前类目配置，否则类目调整会改变历史需求含义。

### 5.3 Region与ServiceArea

Region维护行政区划或平台使用的区域编码；ServiceArea记录服务商覆盖区域及生效时间。地址信息和服务区域匹配逻辑应分开，不能把用户精确地址直接作为公开展示数据。

## 6. 需求与撮合模型

### 6.1 Demand：服务需求

Demand表示业主提出的一次服务需求，关联创建用户、需求所属个人或组织（如适用）、服务类目及类目版本、服务地址及隐私访问规则、需求字段快照、预算、期望工期和附件、审核状态和撮合状态、需求来源和关闭原因。

需求是撮合入口，不等于合同，也不等于已确认工程量。

### 6.2 Match与Invitation

Match表示需求与服务商之间的一次匹配关系；Invitation表示邀请某个服务商参与报价的事件。应保留匹配来源，例如自主申请、平台推荐、人工邀请或定向邀请。匹配结果不能直接创建合同或资金义务。

### 6.3 DemandEvent

需求的关键状态变化和操作应形成事件记录，例如提交、审核通过、退回补充、暂停、恢复、关闭和转入合同。事件记录与当前状态分开，以便审计和排查。

## 7. 报价模型

### 7.1 Quotation与QuotationVersion

Quotation表示某服务商针对某需求的一组报价关系；QuotationVersion表示每次提交的不可覆盖版本。报价版本应包含报价服务主体和实际履约主体、报价总价和计价方式、服务范围及排除项、预计工期和报价有效期、付款建议、售后承诺、条款及附件快照、提交人和提交时间。

### 7.2 QuotationLine

QuotationLine表示报价明细，如人工、材料、设备、施工项目和其他费用。每行记录计量单位、数量、单价、金额、说明和必要税务属性。

金额精度、币种和舍入规则必须统一定义；人民币金额建议使用定点精度，不使用浮点数作为财务计算依据。

### 7.3 报价选择关系

Demand可以关联多个Quotation；简单住宅场景中通常选择一个有效报价形成一份合同。若需求拆成多个服务包并由多个服务商履约，应显式建立服务包/分单关系，不应依赖一对多报价的隐式推断。

## 8. 合同与变更模型

### 8.1 Contract

Contract代表双方或多方之间的一份合同关系。至少明确合同编号和类型、关联需求/报价/订单、签约主体、实际履约主体、收款权利主体、平台在该交易中的角色、合同金额和计价方式、生效/履行/解除/终止时间及当前状态。

合同参与方不能只保存User ID；必须支持个人主体和组织主体。

### 8.2 ContractParty

ContractParty表达合同中的不同法律角色，例如发包方、服务提供方、实际履约方、付款义务方、收款权利方及其他依法约定的参与方。一个主体可以承担多个角色，但应逐一明确。

### 8.3 ContractVersion

合同正文和附件以版本形式保存。每个版本记录内容摘要或文件引用、生成时间、签署状态、双方确认记录和生效时间。已确认版本不可原地覆盖。

### 8.4 ContractChange

ContractChange记录履行期间的范围、工程量、材料、价格、工期或其他条款变化。变更须关联原合同版本、提出方、证据、双方确认和新版本。未确认变更不能进入已确认应付金额。

## 9. 住宅服务履约模型

### 9.1 ServiceOrder

ServiceOrder是住宅服务履约主对象，关联Demand、被接受的QuotationVersion、Contract及生效ContractVersion、需求方和服务提供方主体、实际履约主体、服务地址和类目快照、订单金额及计价方式、履约状态和关键时间。

一个合同可以对应一个住宅服务订单；若合同约定分阶段或多个独立服务包，需按实际履约结构扩展，不能假设永远一对一。

### 9.2 Schedule

Schedule表示预约和排期，可记录进场时间、现场联系人、双方确认、变更历史和无法进场原因。排期调整不自动修改合同工期，除非双方依约确认变更。

### 9.3 WorkLog

WorkLog记录施工过程，包括阶段、时间、施工人员、现场负责人、施工内容、材料使用、图片/视频证据和异常说明。重要记录不允许无痕删除；更正应产生新记录或更正事件。

### 9.4 MaterialUsage

MaterialUsage表示某订单实际使用的材料记录，包含材料描述、品牌型号、规格、数量、批次或凭证（适用时）、提供方和确认情况。它不等同于平台材料商城商品，也不自动代表材料质量已获认证。

### 9.5 Acceptance与Rectification

Acceptance记录每次验收申请和验收结论；Rectification记录整改事项、责任方意见、完成情况和复验结果。允许多轮整改，历史结论不得覆盖。

### 9.6 OrderEvent

订单状态和关键履约动作通过事件记录留痕。当前状态是便于查询的投影，事件历史用于追溯。状态转换必须经过业务规则校验。

## 10. 商业工程项目模型

商业工程需要独立于住宅ServiceOrder建模。

### 10.1 Project

Project表示一个商业工程项目，包含发包主体、项目基本信息、地点、项目类别、项目阶段、预算信息（按权限）、项目资料和风险标记。

### 10.2 ProjectPackage

ProjectPackage表示项目下可独立发包或组织报价的专业包/标段，例如给排水、电气或其他专业工作范围。一个项目可以包含多个Package；每个Package有独立范围、资格要求、报价和履约安排。

### 10.3 Bid与BidEvaluation

Bid表示承包商或服务企业针对项目/专业包提交的投标或报价资料；BidEvaluation记录资格审查、评审维度、评审人、时间和结论。是否适用法定招标程序必须由项目属性和法律要求决定，不能把平台普通报价功能直接称为法定招投标。

### 10.4 ProjectContract

ProjectContract表示项目或专业包对应的合同。一个Project可以关联多份合同；每份合同有独立签约方、履约方、工程范围、付款条件和责任边界。

### 10.5 ProgressClaim、Inspection与FinalSettlement

- ProgressClaim：施工单位申报阶段工程量或进度款。
- Inspection：阶段验收、专业验收或其他约定检查记录。
- VariationOrder：工程签证和合同变更。
- FinalSettlement：竣工结算及相关确认记录。
- WarrantyObligation：质保义务及质保期内事项。

商业工程可能涉及总包、专业分包、供应商和多个实际施工队伍。必须保存合同链和实际履约关系，不能只存一个“项目负责人”。

## 11. 支付与资金数据模型

本领域记录业务支付编排和外部机构交易事实，不建立可自行划转的用户资金钱包。

### 11.1 PaymentPlan

PaymentPlan表示合同约定的付款计划。每个节点关联合同版本、触发条件、应付金额、到期时间和确认依据。合同变更后形成新的计划版本或调整记录，保留历史。

### 11.2 PaymentIntent

PaymentIntent表示平台为某项业务创建的一次支付请求，记录业务对象、付款义务方、收款权利主体、金额、支付用途、合作机构和幂等业务编号。它不是资金账户，也不表示资金已经到账。

### 11.3 PaymentTransaction

PaymentTransaction记录合作银行或持牌支付机构返回的交易流水和状态。保留外部机构交易号、平台请求号、金额、时间、结果和原始通知的安全摘要/必要证据。回调必须验签、去重并支持主动查询。

### 11.4 Refund

Refund关联原支付交易，记录申请原因、申请主体、金额、审批/确认、外部退款请求号和最终结果。部分退款、多次退款和退款失败均应可表达。

### 11.5 Settlement与Reconciliation

Settlement记录合作机构提供的结算批次或结算结果；Reconciliation记录平台业务记录与机构交易/结算文件的核对结果、差异类型和处理状态。

平台服务费应独立记录应收依据、计费规则版本、开票主体和收款结果，不能把平台服务费和服务商工程款混成一笔不透明的资金。

### 11.6 MerchantAccount

MerchantAccount只保存合作机构商户号、商户主体映射、进件状态和必要的非敏感配置引用。不得保存支付机构托管资金的虚构余额；敏感密钥和凭证应进入专门密钥管理设施，不写入普通业务数据。

### 11.7 财务一致性约束

- 金额使用明确币种和定点精度。
- 同一外部交易通知可重复到达，业务处理必须幂等。
- 支付成功、退款成功和结算成功分别依据外部机构事实。
- 任何人工调整必须有授权、原因、证据和审计记录。
- 对账差异不能通过直接覆盖原流水消除，应记录差错处理事件。
- 平台不得将业务台账、积分或虚拟余额描述为法定支付账户。

## 12. 售后、争议与评价模型

AfterSalesCase表示合同履行后的售后请求，关联订单或项目合同、发起方、责任主体、问题类型、处理期限和结果。

Complaint表示平台投诉；Dispute表示交易双方对合同、质量、价款、工期或责任产生的争议。两者可以关联，但概念不同：投诉是向平台提出的治理请求，争议是交易主体之间的实体分歧。

WarrantyObligation关联具体合同条款、责任主体、范围、起止时间和除外条件。质保期限和责任不能由平台统一臆定，应来自合同和适用法律。

Review保存真实交易评价及审核/申诉状态。CreditEvent保存可追溯履约事实，例如按期完成、取消、投诉成立或违规处理。信用分是平台规则计算的派生指标，不是事实本身；必须能解释其数据来源和规则版本。

## 13. 文件、消息与证据

FileAsset管理文件元数据，包括文件类型、存储位置引用、大小、格式、上传者、上传时间、访问等级、扫描状态和生命周期。文件二进制进入对象存储等文件设施，业务库保存元数据和受控引用。

Evidence表示具有业务证明用途的证据描述；EvidenceLink将证据关联到需求、报价、合同、施工记录、验收、支付或投诉等业务对象。原始文件和证据关联不能因业务对象状态变化而被静默删除。

Message用于会话内容；Notification用于系统事件通知和投递记录。短信、推送和站内通知的送达状态不能等同于对方已阅读或法律意义上的有效送达。合同通知等重要事项应根据业务和法律要求设计可验证的通知机制。

## 14. 审计、事件和规则版本

### 14.1 AuditEvent

AuditEvent记录谁在何时以什么身份对哪个对象执行了什么操作，至少包含操作者用户ID、组织ID（适用时）、动作类型、目标类型和目标ID、操作前后状态摘要、操作原因、请求追踪标识、时间和来源信息、授权校验结果。

审计记录应采用受控写入、访问审计和防篡改措施。具体保留期限按法律要求、争议风险和业务必要性制定。

### 14.2 BusinessEvent

BusinessEvent表达领域事实，例如需求审核通过、报价被接受、合同生效、订单进场、验收通过、支付结果确认。业务事件用于通知、异步任务和分析，不应把任意日志文本当作可靠业务事件。

### 14.3 RuleVersion

RuleVersion记录平台服务费、派单、准入、评价和超时规则的版本、生效时间及适用范围。历史订单应能追溯其适用规则版本，规则更新不得追溯改变已确认的合同权利义务。

## 16. 数据一致性与生命周期原则

1. **主键：** 使用内部稳定ID作为主键；对外展示编号与内部主键分离。
2. **唯一性：** 登录凭证、外部机构交易号、合同编号和幂等业务号分别定义唯一性范围。
3. **版本化：** 报价、合同、需求字段配置、服务目录和平台规则应保留版本。
4. **快照：** 历史订单保存当时的主体名称、类目、地址展示策略、报价和合同版本快照。
5. **软删除限制：** 用户可撤回或关闭部分内容，但合同、支付、退款、审计和争议证据不能因普通删除操作而消失；具体保留和删除应符合个人信息保护及档案义务。
6. **状态机：** 状态转换由领域规则控制，不能允许前端任意写入状态字段。
7. **并发控制：** 报价接受、合同确认、变更确认、验收和退款等关键动作需要版本校验或并发控制。
8. **幂等：** 支付回调、退款回调、通知消费和重复提交必须具备幂等机制。
9. **事务边界：** 同一业务模块内的关键状态更新尽量使用本地事务；跨模块或外部机构流程采用可靠消息、状态查询和补偿机制，不假设分布式事务天然可靠。
10. **时间：** 数据库存储统一时间基准，业务展示按交易所在地时区处理；记录业务发生时间和系统接收时间。
11. **金额：** 统一币种、精度、税额口径和舍入规则；禁止用浮点数进行财务金额计算。
12. **隐私：** 身份证件、精确地址、联系方式、合同附件和现场影像按最小必要原则授权访问、脱敏展示和审计。
13. **数据归属：** 明确平台、交易主体和第三方机构各自的数据来源、处理目的、访问权限及共享依据。
14. **分析数据：** 运营报表可使用派生数据和聚合数据，但不能反向替代合同、支付和结算原始事实。

## 17. MVP数据建设优先级

### P0：上线交易闭环必需

用户账户、个人资料和组织主体；组织成员及授权关系；服务商档案、服务能力和准入状态；服务类目和区域；需求、需求事件和附件；撮合关系、报价及报价版本；合同、合同主体、合同版本和变更；住宅服务订单、预约、施工记录和验收；付款计划、支付请求、外部支付流水、退款和对账；投诉/售后工单；审计事件和消息通知。

### P1：城市增长阶段

多城市服务区域和服务商容量；更细的材料使用及采购关联；评价和可解释信用指标；自动派单规则及规则版本；多角色组织工作台和运营分析；服务商排期和履约能力预测。

### P2：工程和供应链扩张

Project、ProjectPackage、Bid和BidEvaluation；ProjectContract、ProgressClaim、Inspection和FinalSettlement；供应商、商品目录、采购订单和交付；多合同、多施工队伍和多主体结算关系；暖通、消防、弱电和机电等新专业目录。

## 18. 首期暂不建设的复杂能力

在业务尚未验证前，不建议自建可充值、可提现、可转账的用户资金钱包；自建资金池或平台内部清算系统；复杂多级分账引擎；全行业统一工程造价和自动审价引擎；未经实际项目验证的全套招投标系统；过早采用微服务、跨地域分布式数据库和多活架构；把所有施工过程抽象成难以运营配置的高度通用工作流平台。

## 19. 数据模型待确认事项

进入数据库逻辑模型前，需要业务方确认：

1. 首期服务商是否允许自然人直接作为合同签约和收款主体，还是仅允许个体工商户/企业入驻。
2. 一个住宅需求是否允许拆成多个服务包，由多个服务商分别签约履约。
3. 平台是否允许同一订单出现签约主体、实际履约主体和收款权利主体不同的情况；若允许，需定义授权、披露和核验要求。
4. 住宅服务首期是否支持材料由业主自购、服务商代购和平台供应商供货三种模式。
5. 合作支付机构是否支持平台目标业务所需的商户进件、交易资金结算、退款和分账产品，以及各自适用条件。
6. 商业工程是否在首期只做项目线索和撮合，还是需要进入合同及进度款管理。
7. 用户身份核验、合同证据、施工影像、支付记录和投诉资料分别需要怎样的访问与保存策略。

这些问题会影响实体关系和交易约束，不应在没有决策的情况下用隐含默认值固化。
